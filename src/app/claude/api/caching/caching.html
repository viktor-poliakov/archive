Prompt caching

Prompt caching — API запоминает начало запроса: инструменты, системный промпт, документы, историю диалога. Если следующий запрос начинается так же, эта часть читается из кэша — в 10 и более раз дешевле обычного входа и заметно быстрее. Чем кэш поставщика отличается от собственного кэша ответов, разобрано в LLM API. Здесь — как включить его в Messages API.

Когда помогает

  • Длинный системный промпт — правила, справочник, примеры ответов, одинаковые для тысяч запросов.
  • Много вопросов к одному документу — договор, кодовая база, выгрузка данных.
  • Чат и агентный цикл — история растёт, и каждый следующий запрос повторяет всю предыдущую.
  • Не поможет, если начало запроса каждый раз разное или короче минимума: 512 токенов у актуальных моделей. Ошибки при этом нет — кэш просто не создаётся.

Claude Code и Managed Agents кэшируют сами, настраивать ничего не нужно. Эта страница — для своего кода поверх API.

Как включить

Проще всего — поле cache_control на уровне запроса. API поставит границу кэша на последний блок и будет сдвигать её по мере роста диалога:

Если конец запроса уникален — например, один общий документ и разные вопросы к нему, — ставьте cache_control вручную на блок, после которого начинается переменная часть. Иначе каждый запрос будет записывать в кэш то, что никто не прочитает:

  • Граница — cache_control на любом блоке: тексте в system, описании инструмента, сообщении, картинке, документе, tool_result. Всё до неё включительно кэшируется.
  • До 4 границ на запрос — например, после инструментов, после справочника и в конце истории.
  • Срок жизни — 5 минут, и каждое чтение продлевает его заново. { type: "ephemeral", ttl: "1h" } — час, для пауз между запросами от 5 минут до часа.

Как устроено

Кэш — это совпадение начала запроса байт в байт. API собирает запрос в порядке tools → system → messages и сравнивает его начало с тем, что прошлые запросы записали до своих границ. Любое изменение в каком-то месте сбрасывает кэш для всего, что идёт после него. Отсюда главное правило: неизменное — в начало, переменное — в конец.

  • Кэш живёт внутри рабочего пространства (workspace) Claude Console и между организациями не делится.
  • Параллельные запросы с одинаковым началом кэш друг другу не дают: он появляется, только когда первый ответ начал приходить. Для веерной рассылки отправьте один запрос, дождитесь первого токена, потом остальные.

Сколько стоит

ОперацияЦена относительно обычного входа
Запись в кэш на 5 минут×1,25
Запись в кэш на час×2
Чтение из кэша×0,1. У Opus 5.5 — ×0,05, у Fable 5.1 — ×0,025

С 5-минутным кэшем выгода начинается уже со второго запроса: 1,25 + 0,1 против 2. С часовым — с третьего. В Claude API чтения из кэша к тому же не расходуют лимит входных токенов в минуту у большинства моделей.

Как проверить

Ответ сам говорит, сработал ли кэш:

  • Весь вход = input_tokens + cache_creation_input_tokens + cache_read_input_tokens. Маленький input_tokens — не ошибка, остальное пришло из кэша.
  • cache_read_input_tokens равен нулю на повторяющихся запросах — значит, начало каждый раз чем-то отличается. Ищите это в таблице ниже.
  • Проверяйте после каждого изменения сборки промпта. Сломанный кэш ничем не выдаёт себя, кроме счёта.
