Экосистема/Бэкенд/Python

Python

Python — второй по распространённости язык бэкенда после JavaScript, и попал он туда необычным путём. Node пришёл в веб из браузера, а Python — из научных лабораторий, системного администрирования и обработки данных. Из-за этого у него другие сильные стороны: там, где Node просто «тоже умеет», Python часто оказывается единственным разумным вариантом. На этой странице разберём, как язык выглядит и читается, три главных каркаса (Flask, FastAPI, Django), страшное слово GIL, которое означает почти то же самое, что «один поток» из прошлой страницы, и честно ответим, когда Python стоит брать, а когда нет.

Как это выглядит и почему без скобок

Первое, что бросается в глаза человеку с JavaScript: в Python нет фигурных скобок и точек с запятой. Вложенность задаётся отступами, и они не оформление, а часть синтаксиса.

Реакция обычно одинаковая: «а если случайно сдвинуть строку?» Ответ: получите другую программу или ошибку. Именно поэтому в Python-проектах отступы никогда не обсуждают — их расставляет автоформатировщик, и спорить не о чем.

Зачем так сделано. Логика простая: в любом языке аккуратные программисты и так выравнивают код отступами, чтобы его было видно глазами. Раз отступ всё равно есть и всё равно означает вложенность — зачем дублировать ту же мысль ещё и скобками? Побочный эффект оказался ценнее задумки: любой код на Python выглядит примерно одинаково, потому что криво отформатированный просто не работает.

Дальше идут вещи, которые вы уже знаете, — только называются иначе:

Массив здесь называется списком, объект — словарём, this — self, шаблонные строки — f-строками. Конструкция [p for p in products if ...] выглядит непривычно, но читается почти как фраза: «взять p для каждого p из products, если выполнено условие» — это аналог связки map и filter.

Про читаемость без рекламы. У Python репутация «самого понятного языка», и она в основном заслуженная: код действительно похож на псевдокод из учебника, а обязательные отступы не дают ему превратиться в кашу. Но не ждите, что от этого станет проще бэкенд. Базы данных, транзакции, права доступа и очереди сложны сами по себе — на любом языке одинаково.

Типы: есть, но никто не заставляет

Python — язык с динамической типизацией, как и JavaScript: переменная может содержать что угодно. Но с версии 3.5 в нём есть подсказки типов, и в серьёзных проектах ими пользуются повсеместно.

Здесь есть отличие от TypeScript, которое обязательно надо усвоить, иначе будет очень обидно. В TypeScript типы тоже стираются при сборке — но код с ошибкой типов просто не соберётся: компилятор стоит на пути и не пропустит.

В Python на пути не стоит никто. Подсказки типов — это комментарии, которые понимает редактор. Программа с грубым несоответствием типов запустится как ни в чём не бывало и упадёт уже во время работы. Чтобы проверка действительно произошла, надо отдельно запустить инструмент — mypy или pyright — и включить его в автоматические проверки проекта.

TypeScript Python с подсказками типов
Типы обязательны? Нет, но проверка встроена в сборку Нет, и проверки по умолчанию нет вообще
Кто проверяет ✅ компилятор, всегда отдельный инструмент, если вы его запустили
Код с ошибкой типов ✅ не соберётся ❌ запустится и упадёт во время работы
Проверка данных от клиента ❌ нужна отдельная библиотека ✅ Pydantic делает это из тех же аннотаций

Последняя строка — приятный сюрприз, и на нём построен весь FastAPI, к которому мы сейчас перейдём.

Три каркаса и как между ними выбрать

В мире Python три основных каркаса, и различаются они тем же, чем различались фреймворки на клиенте: количеством решений, принятых за вас.

Flask — минимальный

Flask по духу — это Express мира Python. Даёт маршруты и почти ничего сверх. Понятен за десять минут, но структуру, проверку данных и работу с базой вы собираете сами.

Строка со значком @ над функцией называется декоратором. Читается как «этот адрес обслуживает вот эта функция». Если вы видели Angular или NestJS — это ровно та же идея записи.

FastAPI — современный выбор

Главная идея FastAPI: раз вы всё равно пишете подсказки типов, пусть они работают по-настоящему. Из класса CreateOrderRequest каркас сам делает три вещи:

  • Проверяет входящие данные. Прислали строку вместо числа или количество 0 — обработчик даже не вызовется, клиент получит 422 с точным указанием, какое поле не подошло.
  • Подсказывает в редакторе. Внутри функции data — не безымянный словарь, а объект с известными полями.
  • Собирает документацию. Открываете адрес /docs — и там готовая интерактивная страница со всеми вашими адресами и формами для пробных запросов. Писать её не нужно вообще.

Последний пункт стоит оценить отдельно. Актуальная документация API — вечная боль команд: её пишут отдельно, забывают обновить, и через полгода она врёт. Здесь она собирается из того же кода, который обрабатывает запросы, — а значит, не может разойтись с действительностью. Формат этого описания называется OpenAPI, и про него подробнее — на странице Контракты API.

Django — всё в комплекте

Django исповедует принцип «батарейки в комплекте»: типовые задачи веба решены заранее. Вы описываете данные — и получаете таблицы в базе, язык запросов, формы, систему пользователей и права.

Но настоящий козырь Django — готовая административная панель. Три строки кода — и у вас полноценная панель управления со списками, поиском, фильтрами, созданием и редактированием записей. На других языках такое пишут неделями.

GIL: страшное слово, знакомая мысль

Про Python вы обязательно услышите аббревиатуру GIL и обычно с интонацией «вот поэтому он не годится». Разберёмся спокойно.

GIL расшифровывается как «глобальная блокировка интерпретатора» и означает следующее: внутри одного процесса Python код выполняет один поток за раз, даже если вы создали десять потоков.

Заметили? Это ровно та же граница, что и в Node на прошлой странице, только достигнутая другим механизмом:

Что делает сервер Node.js Python с GIL
Ждёт базу, сеть, диск ✅ поток свободен, берёт другие запросы ✅ GIL отпущен, другие потоки работают
Считает в цикле ❌ блокирует всех ❌ блокирует всех в этом процессе
Как обойти воркеры, очередь, несколько копий несколько процессов, библиотеки на C, очередь

Аналогия: одна касса и один пропуск. Представьте офис, где может работать много сотрудников, но говорить по телефону разрешено только тому, у кого в руках единственный пропуск. Пока сотрудник говорит — остальные ждут. Но как только он уходит на обед (то есть начинает ждать внешнего события), он кладёт пропуск на стол, и его берёт следующий. Если все сотрудники в основном ждут — офис работает прекрасно. Если все хотят говорить одновременно — очередь.

Второй путь в этом примере — самый важный для понимания репутации Python. Фраза «Python медленный» верна применительно к самому языку и совершенно неверна применительно к тому, как его используют. В обработке данных и машинном обучении Python — это пульт управления: вы пишете три понятные строки, а считает высокооптимизированный код на C и видеокарта. Скорость самого Python при этом не имеет значения.

Два мира: синхронный и асинхронный

Тут есть особенность, которой нет ни в Node, ни в Go: в Python веб-разработка существует в двух параллельных вариантах, и путать их болезненно.

Ловушка, на которой обжигаются все. Вы взяли FastAPI ради асинхронности, а внутри обработчика вызвали привычную библиотеку requests — синхронную. Она не умеет отпускать поток, и на время её работы весь цикл событий стоит. Асинхронность превращается в тыкву, причём молча: ошибок нет, просто сервер держит не тысячу пользователей, а десять. Правило: асинхронный каркас — асинхронные библиотеки (httpx вместо requests, asyncpg вместо синхронного драйвера базы).

ORM и главная ошибка производительности

Работа с базой — сильная сторона Python. Здесь принято обращаться к данным не строками SQL, а объектами языка. Такой слой называют ORM (объектно-реляционное отображение).

Обратите особое внимание на вторую половину примера. Ошибка «N + 1» — самая частая причина медленных страниц во всём вебе, и делают её на всех языках одинаково. Код выглядит совершенно невинно: цикл по заказам, внутри обращение к пользователю. А в базу при этом уходит сто один запрос вместо одного.

Коварство в том, что на вашей машине с двадцатью тестовыми заказами всё летает. Проблема появляется только на боевых данных — и появляется резко.

Как поймать это заранее. Включите в режиме разработки вывод всех SQL-запросов в консоль. Открыли страницу, увидели в журнале сто одинаковых запросов подряд — нашли проблему за минуту. В Django для этого есть отдельная панель отладки, которая показывает число запросов прямо на странице. Подробнее про устройство баз — в подразделе Данные и хранилища.

Настоящая суперсила: то, что рядом с вебом

А теперь главное, ради чего Python вообще стоит рассматривать. Как веб-язык он хорош, но не уникален — Node и Go делают ту же работу не хуже. Уникальным его делает всё, что находится рядом.

Разберём, почему это важно для выбора языка на бэкенде. Представьте интернет-магазин, которому через год понадобится:

  • Аналитика — сводные отчёты по продажам, когорты покупателей, прогноз спроса.
  • Рекомендации — «с этим товаром часто покупают».
  • Обработка отзывов — автоматическая оценка тональности или выжимка.
  • Функции на основе ИИ — поиск по смыслу, помощник в поддержке, генерация описаний.

Если бэкенд на Python, всё это добавляется в тот же проект теми же людьми. Если бэкенд на другом языке — в компании появляется второй язык, второй набор инструментов и вечный вопрос, как две части между собой связывать.

Про ИИ отдельно. Практически все официальные библиотеки для работы с языковыми моделями выходят сначала на Python, а всё, что связано с обучением моделей, существует только на Python. Это не мода, а сложившаяся за пятнадцать лет экосистема. Если в вашем продукте предполагается что-то содержательное на основе ИИ — этот аргумент часто перевешивает все остальные. Подробнее — в подразделе ИИ в продукте.

Как это запускают в бою

Здесь есть неочевидная деталь, на которой спотыкаются все новички.

Команда python manage.py runserver, которую вы увидите в каждом учебнике, — это сервер для разработки. Он однопоточный, медленный и не рассчитан на посторонних. В бою вместо него ставят отдельный сервер приложений: gunicorn для синхронных каркасов, uvicorn для асинхронных.

Параметр --workers — это количество процессов-копий вашего приложения. Помните про GIL? Один процесс использует одно ядро. Четыре процесса — четыре ядра. Обычный ориентир — по числу ядер машины.

Виртуальное окружение — обязательная привычка. Без него пакеты ставятся в систему целиком, и два проекта, которым нужны разные версии одной библиотеки, начинают конфликтовать. Команда python -m venv .venv создаёт проекту собственную папку с пакетами — по смыслу это тот же node_modules, только его надо завести явно. Из современных инструментов стоит знать uv: он делает то же самое, что pip, но в разы быстрее.

Когда Python — правильный выбор

Продукт с аналитикой, рекомендациями или ИИ ✅ лучший выбор Весь мир данных и машинного обучения живёт здесь. Не придётся заводить второй язык.
Магазин, CRM, портал с админкой ✅ отлично Django даёт готовую панель управления, пользователей и права почти бесплатно.
API для мобильного приложения ✅ отлично FastAPI: проверка данных и документация собираются сами из типов.
Автоматизация, интеграции, разбор выгрузок ✅ язык по умолчанию Для любого формата и любого API есть готовая библиотека.
Первый язык для обучения бэкенду ✅ хороший вариант Читаемый синтаксис, много материалов, широкий рынок.
Высоконагруженная система с жёсткими требованиями к задержке ❌ не лучший Python в разы медленнее компилируемых языков. Здесь смотрят на Go.
Сервис с очень экономным потреблением памяти ❌ плохо Синхронная модель требует процессов, а каждый процесс стоит десятки мегабайт.
Серверный рендеринг React-приложения ❌ мимо Нужен тот же язык, что и на клиенте, — то есть Node.

Честно про скорость. Python действительно медленный как язык — раз в десять-пятьдесят медленнее Go на чистых вычислениях. Но помните вывод предыдущей страницы: обычное веб-приложение почти всё время ждёт базу, а не считает. На фоне ожидания в 40 миллисекунд разница между 0,1 и 2 миллисекундами вашего кода незаметна. Скорость языка становится решающей заметно реже, чем принято думать, — а вот наличие нужных библиотек решает почти всегда.

Коротко

  • Отступы вместо скобок — часть синтаксиса. Из-за этого любой Python-код выглядит одинаково: криво отформатированный просто не работает.
  • Подсказки типов есть, но никто не проверяет их сам. В отличие от TypeScript, код с ошибкой типов запустится. Проверка — отдельный инструмент (mypy), который надо включить осознанно.
  • Три каркаса под три ситуации: Flask — минимум, FastAPI — проверка данных и документация из типов, Django — всё в комплекте плюс готовая админка.
  • GIL — это «один поток» другими словами. Пока код ждёт сеть или базу, ограничение не мешает; как только начинает считать — упирается. Обходят процессами, библиотеками на C или очередью.
  • «Python медленный» — правда про язык и неправда про применение. В обработке данных он пульт управления, а считает код на C и видеокарта.
  • Два мира — синхронный и асинхронный, и смешивать их нельзя: одна синхронная библиотека внутри асинхронного обработчика молча убивает всю асинхронность.
  • ORM удобна, но приносит ошибку «N + 1»: цикл по ста заказам с обращением к пользователю внутри — это сто один запрос вместо одного. Самая частая причина медленных страниц.
  • Главная причина выбрать Python — не веб, а то, что рядом: аналитика, машинное обучение, работа с ИИ, автоматизация. Здесь у него практически нет конкурентов.
  • В бою нужен отдельный сервер приложений (gunicorn или uvicorn) и виртуальное окружение — встроенный runserver для боя не предназначен.

Дальше — Go: язык, устроенный по противоположному принципу. Если Python старается дать вам как можно больше способов сделать что угодно, то Go сознательно даёт как можно меньше — и мы разберём, почему это оказалось преимуществом. Заодно посмотрим, как решается проблема, из-за которой мы дважды упирались в «один поток». Общие обязанности сервера — на странице Что делает бэкенд.
