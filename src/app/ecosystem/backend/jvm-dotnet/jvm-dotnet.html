Java, Kotlin, C#/.NET

Это территория, о которой новичок из мира JavaScript обычно не знает почти ничего, — а между тем на ней держится большая часть банков, страховых, телекома, авиаперевозок и вообще всего, что должно работать десятилетиями. Здесь ценят не краткость и не скорость разработки, а другие вещи: предсказуемость, инструменты и уверенность, что систему, написанную в 2014 году, можно будет обновлять и в 2034-м. Три языка объединены в одну страницу не случайно: устроены они очень похоже, и, поняв один, вы почти бесплатно понимаете остальные два.

Общая идея: программа для выдуманного компьютера

Начнём с механизма, который объединяет все три языка и который стоит понять до всего остального. Есть три способа превратить написанный текст в работающую программу:

Третий способ и есть то, что объединяет Java, Kotlin и C#. Компилятор превращает ваш код не в команды конкретного процессора, а в байт-код — команды выдуманного, несуществующего компьютера. А выполняет эти команды виртуальная машина: JVM для Java и Kotlin, CLR для C#.

Аналогия: чертёж в метрической системе. Вы проектируете деталь и делаете чертёж в миллиметрах — в единицах, понятных всем. Дальше чертёж отдают на любой завод мира: японский станок, немецкий станок, американский станок. Каждый завод сам переводит миллиметры в свои внутренние команды. Вам не нужно делать три разных чертежа. Байт-код — это чертёж, виртуальная машина — завод, который умеет по нему работать.

Про «прогрев» стоит знать заранее. Первые секунды после запуска Java-приложение работает медленно, а через минуту выходит на полную скорость. Для сервера, который живёт месяцами, это неважно вообще. А вот для serverless-функции, которая поднимается заново на каждый запрос, это беда — и именно поэтому в том мире Java исторически проигрывает Go. Частично лечится заранее скомпилированными сборками (GraalVM для Java, AOT для .NET).

Java: правда и устаревшие стереотипы

Главная претензия к Java — многословность. Претензия справедливая, но заметно устаревшая. Посмотрите на разницу:

Сорок строк превратились в одну. Ключевое слово record появилось в 17-й версии языка, и вместе с ним пришло ещё много удобного. Проблема в том, что оба утверждения верны одновременно: современная Java компактна, а в живых проектах десятилетней давности вы увидите верхний вариант.

Практическое следствие при чтении статей и вакансий. Смотрите на версию. Java 8 (2014 год) и Java 21 (2023 год) — это языки, отличающиеся почти так же сильно, как JavaScript до и после появления классов и промисов. Если статья ругает Java за многословность, а датирована 2015 годом, — половина её претензий уже неактуальна.

Третий ответ на вопрос о параллельности

Мы уже видели два подхода: Node с одним потоком и циклом событий, Go с дешёвыми горутинами. Java даёт третий — настоящие потоки операционной системы.

Модель «один запрос — один поток» имеет большой плюс, который трудно оценить, пока не поработаешь с асинхронным кодом: код пишется линейно. Никаких async, никаких размышлений «а не заблокирую ли я цикл событий», никакой боязни случайно вызвать синхронную библиотеку. Тяжёлое вычисление — тоже не проблема: оно займёт одно ядро из шестнадцати, остальные продолжат работать.

Минус — цена потока. Около мегабайта памяти каждый, поэтому их не может быть много. И вот здесь произошло самое интересное изменение за последние годы:

Подход Как пишется код Цена одной единицы Тяжёлые вычисления
Node.js ❌ асинхронно, с оглядкой на цикл событий ✅ почти бесплатно ❌ блокируют всех
Python (синхронный) ✅ линейно ❌ процесс: десятки МБ занимает одно ядро
Go ✅ линейно ✅ горутина: ~2 КБ ✅ одно ядро из многих
Java (классика) ✅ линейно ❌ поток ОС: ~1 МБ ✅ одно ядро из многих
Java 21+ (виртуальные потоки) ✅ линейно, код не меняется ✅ около килобайта ✅ одно ядро из многих

Последняя строка — это, по сути, горутины, приехавшие на JVM. И самое ценное в них то, что код не приходится переписывать: вы пишете обычный блокирующий код, а под капотом он перестаёт занимать настоящий поток на время ожидания. Java получила выгоду асинхронности, не заставив разработчиков поменять привычки.

Spring Boot: почему он везде

На JVM есть один безусловно доминирующий каркас, и это Spring. Разберём его центральную идею, потому что она встречается и за пределами Java.

Внедрение зависимостей — идея, которая звучит сложно, а означает простое. Без неё класс сам создаёт всё, что ему нужно: базу, почтовый сервис, платёжный шлюз. И тогда его невозможно протестировать, не подняв настоящую базу и не отправив настоящее письмо.

С внедрением класс только объявляет: «мне нужен сервис заказов». Кто именно его предоставит — решает каркас: в бою настоящий, в тестах подделка. Если вы видели Angular или NestJS — это ровно та же идея, и там она появилась под влиянием Spring.

Обратите внимание на первый блок примера — он производит впечатление даже на опытных людей из других экосистем. Вы объявляете интерфейс с методом findByUserIdAndStatus, не пишете никакой реализации, и Spring собирает SQL-запрос, прочитав имя метода. Это не преувеличение и не шутка — так действительно работает.

Честная плата за «батарейки в комплекте». Минимальное Spring-приложение стартует несколько секунд и занимает сотни мегабайт памяти. Для банковской системы это не имеет значения. Для маленького сервиса, который должен подниматься за миллисекунды и жить в контейнере на 64 мегабайта, — имеет, и очень.

Kotlin: Java без боли

Kotlin работает на той же виртуальной машине, пользуется теми же библиотеками и спокойно живёт в одном проекте с Java — файлы двух языков могут вызывать друг друга. Но пишется он заметно приятнее.

Три отличия стоит разобрать отдельно:

  • Краткость. Класс данных — одна строка вместо сорока. Функции из одного выражения пишутся через знак равенства без фигурных скобок.
  • Защита от пустых значений в системе типов. Это главное. Тип String не может быть пустым — компилятор не даст. Хотите разрешить пустоту, пишете String?, и тогда компилятор заставит её обработать. Обращение к пустому значению — самая частая ошибка времени выполнения за всю историю Java; её автор публично назвал эту идею «ошибкой на миллиард долларов». Kotlin переносит её из времени работы в время сборки.
  • Корутины. Те же горутины, только на JVM: очень дешёвые единицы параллельности плюс удобный способ запустить три запроса одновременно и дождаться всех.

Где Kotlin господствует безусловно — это Android. Google объявил его основным языком платформы, и новые мобильные приложения на Java почти не пишут. Для бэкенда Kotlin — приятная альтернатива Java, но не революция: экосистема, инструменты и каркасы те же самые. Компания, у которой уже есть Java-проекты, может начать писать новые части на Kotlin, ничего не ломая, — и многие так и делают.

C# и .NET: зеркальная история

C# устроен настолько похоже на Java, что человек, знающий один язык, читает код на другом почти свободно. Своя виртуальная машина, своя строгая типизация, свой огромный каркас, свой мир корпоративной разработки.

Два момента, на которые стоит посмотреть.

Первый: стереотип про многословность устарел и здесь. Современный ASP.NET Core с минимальными API компактнее многих примеров на Node из прошлых глав, а зависимости подставляются прямо в аргументы функции-обработчика.

Второй: LINQ — способ писать запросы к данным как обычный код. То, что в других экосистемах делают библиотеки-ORM, здесь встроено в сам язык, и опечатка в имени поля становится ошибкой сборки, а не пустым результатом в бою.

Про «C# только под Windows» — это давно неправда. Так было до 2016 года. Современный .NET работает на Linux и macOS, отлично живёт в контейнерах, и значительная часть серверов на нём — линуксовые. Если встретите утверждение об обратном, посмотрите на дату статьи.

Признак Java Kotlin C#
Виртуальная машина JVM JVM (та же) CLR
Главный каркас Spring Boot Spring Boot или Ktor ASP.NET Core
Многословность средняя (была высокой) ✅ низкая низкая
Защита от пустых значений ❌ частичная, через пометки ✅ встроена в типы есть, включается настройкой
Вторая большая ниша большие корпоративные системы ✅ разработка под Android игры на Unity, приложения для Windows
Рынок труда ✅ огромный растёт, во многом за счёт Android ✅ большой

Деньги и транзакции: почему это важно именно здесь

Раз уж речь зашла о банках, разберём две вещи, которые в этом мире считаются азбукой, а в вебе о них часто узнают поздно.

Первая — транзакция. Мы уже встречали её на странице про Go, но здесь она выглядит проще некуда: одна пометка над методом превращает его в «либо всё, либо ничего». Вылетело исключение — все изменения отменены.

Представьте перевод денег без транзакции: с одного счёта списали, а на второй не зачислили из-за сбоя между двумя строками. Деньги исчезли. Именно этот сценарий и породил само понятие транзакции.

Вторая вещь важна не меньше, и её спрашивают на собеседованиях: деньги нельзя хранить в числах с плавающей точкой. Причина в том, что double не умеет точно представлять десятичные дроби: 0.1 + 0.2 даёт 0.30000000000000004. На одной операции это незаметно, на миллионе — расхождение в отчётах, которое потом ищет бухгалтерия. Правильно: BigDecimal в Java, decimal в C#, либо целые числа в копейках. Кстати, это же ограничение есть и в JavaScript — там вообще нет других чисел, и поэтому в Node суммы почти всегда хранят целыми в копейках.

И третье, о чём стоит знать, — блокировки. Два человека покупают последний товар в одну и ту же миллисекунду. Если оба запроса прочитают «остаток 1» и оба спишут, склад уйдёт в минус. Поэтому строку берут «с замком»: второй запрос подождёт, пока первый закончит. Это универсальная тема для любой базы данных и любого языка, но в корпоративных системах ей уделяют особое внимание — там цена ошибки считается в деньгах.

Почему это выбирают банки

Теперь главный вопрос страницы: почему именно эти платформы стоят там, где цена ошибки измеряется в миллионах. Причины почти не про язык.

Второй пункт стоит развернуть, потому что он редко попадает в статьи, а на практике решает многое. Инструменты диагностики на JVM и .NET — лучшие в отрасли. К работающему в бою приложению можно подключиться и посмотреть, что происходит внутри, не останавливая его: какой поток чем занят, куда уходит память, какой метод съедает процессор.

Когда час простоя стоит миллионы, возможность разобраться в проблеме за пятнадцать минут вместо суток — это и есть настоящий аргумент выбора.

Про среды разработки. IntelliJ IDEA и Visual Studio делают вещи, которых нет в лёгких редакторах: переименовать метод сразу во всём проекте с гарантией, что ничего не сломается; найти все места вызова без пропусков; пройти цепочку вызовов на десять уровней вглубь. На проекте в миллион строк это не удобство, а необходимое условие того, что работа вообще возможна.

Совет для того, кто выбирает первый язык бэкенда. Java и C# — не лучший старт, если вы учитесь сами и хотите быстро увидеть результат: слишком много обвязки до первого работающего экрана. Но это очень хороший второй шаг и отличный выбор, если вы целитесь в конкретную нишу — банки, корпоративные системы или Android. Рынок там большой, зарплаты стабильные, а проекты длинные.

Коротко

  • Все три языка компилируются в байт-код — команды выдуманного компьютера, — а выполняет их виртуальная машина: JVM у Java и Kotlin, CLR у C#. Один собранный файл работает на всех системах.
  • Лишний слой не делает их медленными. Виртуальная машина следит за кодом и компилирует горячие места в машинный код на ходу. Цена — «прогрев»: первые секунды после старта медленно.
  • Java стала заметно компактнее. Сорок строк класса превратились в одну строку с record. Оценивая статью или вакансию, смотрите на версию: Java 8 и Java 21 — очень разные языки.
  • Третья модель параллельности — настоящие потоки. Код пишется линейно, без асинхронности, тяжёлые вычисления не блокируют других. Плата — мегабайт памяти на поток, но виртуальные потоки в Java 21 её сняли, не потребовав менять код.
  • Spring Boot доминирует на JVM. Его центральная идея — внедрение зависимостей: класс объявляет потребность, каркас её удовлетворяет. Та же идея живёт в Angular и NestJS.
  • Kotlin — это Java без боли: короче, с защитой от пустых значений прямо в типах и с корутинами. На Android — безальтернативный выбор.
  • C# устроен почти зеркально Java, давно работает на Linux, а LINQ даёт запросы к данным прямо в языке. Вторая ниша — игры на Unity.
  • Банки выбирают эти платформы не за язык, а за горизонт поддержки в десять лет, лучшие в отрасли инструменты диагностики боевых систем и доступность разработчиков.
  • Плата — вес и скорость старта: сотни мегабайт памяти и секунды на запуск. В корпоративной системе это неважно, в маленьком контейнере и в serverless — критично.

Дальше — PHP и Ruby: два языка с самой несправедливой репутацией в отрасли. На одном работает больше сайтов, чем на всех остальных вместе взятых, а на другом построена значительная часть известных вам продуктов — и оба принято ругать люди, которые не открывали их лет десять.
