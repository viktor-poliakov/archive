Экосистема/Процесс и качество/Git, ветвление, code review

Git, ветвление, code review

В предыдущем подразделе, «Наблюдаемость», мы закончили обход технической части: научились писать код, собирать его, выкладывать на серверы, защищать от чужих рук и следить за тем, как он живёт под настоящей нагрузкой — по логам, метрикам и ошибкам. Всё это описывало продукт, но почти ничего не говорило про людей, которые его делают. А продукт делает не один человек: над одними и теми же файлами одновременно работают двое, трое, десять, и каждый из них что-то правит, ломает, переделывает и передумывает. Подраздел «Процесс и качество» — про то, как команда договаривается работать над общим кодом так, чтобы не мешать друг другу и не терять сделанное. Начинаем с самого низа этого процесса: с Git — программы, которая хранит историю изменений; с ветвления — способа работать над своей задачей, не задевая чужую; и с code review — разговора о коде до того, как он попадёт к пользователям. Эта страница написана для человека, который Git ещё ни разу не открывал: мы разберём три места, где живёт файл, устройство коммита, что такое ветка на самом деле, чем слияние отличается от перебазирования, как разобрать конфликт руками и как выглядит нормальный запрос на слияние. Обещание простое: после неё вы будете понимать не только какие команды набирать, но и что при этом происходит внутри — а значит, сможете выбираться из ситуаций, которые в справочнике не описаны.

Зачем вообще система контроля версий

Прежде чем учить команды, полезно увидеть проблему, которую они решают. Проблема появляется у каждого, кто хоть раз делал что-то дольше одного дня: нужно менять файл и при этом не потерять то, что уже работало. Человек без специальных инструментов решает это единственным доступным способом — копирует папку. Появляются «сайт», «сайт_копия», «сайт_финал», «сайт_финал_2_точно_последний». Посмотрим на этот способ честно, со всеми его последствиями, а потом — на то, как выглядит то же самое с Git.

Главное в этом примере — не список команд, а мысль о том, что копирование папок и правда решает задачу, но решает её плохо в трёх местах сразу. Оно не помнит, почему появилась каждая копия: имя папки хранит порядковый номер, а не причину. Оно не умеет сравнивать: чтобы понять, чем «финал_2» отличается от «финала», нужно открывать оба и читать глазами. И оно не умеет объединять: если вы правили копию, а коллега — оригинал, свести правки можно только вручную. Система контроля версий (version control system) — это программа, которая берёт на себя ровно эти три вещи: хранит причину каждого изменения, показывает разницу между любыми двумя состояниями и умеет сводить параллельные правки. Git — самая распространённая из таких программ.

Стоит сразу разделить два слова, которые новички путают. Git — это программа, которая работает у вас на компьютере и хранит историю в скрытой папке .git внутри проекта. GitHub (а также GitLab, Bitbucket, Gitea) — это сайт, на котором лежит копия репозитория, чтобы к ней был доступ у всей команды. Git прекрасно работает вообще без интернета; хостинг нужен для совместной работы, а не для хранения истории как таковой.

Про «распределённость». Про Git часто говорят «распределённая система». Расшифровывается это очень просто: у каждого участника на диске лежит полная история проекта, а не только последняя версия. Поэтому смотреть историю, создавать ветки и делать коммиты можно в самолёте без сети — сеть нужна только чтобы обменяться сделанным с другими.

Три места, где живёт файл

Это самая важная секция на странице, и если из всего текста вы запомните только её, оно уже окупится. Почти все «непонятные» сообщения Git у новичка растут из одного заблуждения: человек думает, что мест два — файл на диске и «где-то в гите». Мест три, и переход между ними делается тремя разными командами. Пока эта картинка не встала на место, команды выглядят как заклинания; когда встала — становятся очевидными.

Разберём главное. Рабочая папка — это обычные файлы, которые вы видите в проводнике; там царит рабочий беспорядок и ничто ни к чему не обязывает. Индекс — промежуточный список того, что вы намерены сохранить следующим снимком; он существует именно для того, чтобы вы могли сохранить не всё подряд, а один связный кусок работы. Репозиторий — постоянное хранилище, куда попадают коммиты и откуда они уже сами собой не исчезают. Ключевой вывод, который экономит новичку недели: команда git add ничего не сохраняет навсегда, она только откладывает файл в сторону. Сохраняет только git commit.

Зачем вообще нужна средняя ступень, если можно было бы сохранять сразу всё изменённое? Ровно затем, чтобы у вас была возможность собрать коммит осознанно. За полдня работы вы почти наверняка тронете несколько не связанных между собой вещей: поправите ошибку, заодно переименуете переменную, заодно допишете комментарий. Индекс позволяет отобрать из этой кучи один связный кусок и сохранить только его, а остальное оставить на столе до следующего раза. Без такой промежуточной ступени коммит всегда получался бы «всё, что было в папке на момент сохранения», — то есть тем самым большим намешанным коммитом, про который речь пойдёт в отдельной секции.

Частая ошибка первой недели. Человек делает git add ., потом правит файл дальше и удивляется, что в коммит попала старая версия. Всё логично: в коробку положили ту вещь, которая лежала на столе в момент укладки. Правка после git add — это новая вещь на столе. Её надо доложить в коробку ещё раз.

Что такое коммит на самом деле

Слово «коммит» (commit) обычно объясняют как «сохранение». Это верно, но недостаточно, чтобы понимать поведение Git. Коммит — это не «дельта» и не «список правок», а полный снимок состояния проекта плюс небольшая карточка с описанием: кто, когда, зачем и от какого состояния отталкивался. Посмотрим, из чего именно он состоит и почему у него не номер, а длинная строка из букв и цифр.

Здесь важны две вещи. Первая: у каждого коммита есть ссылка на родителя — на то состояние, из которого он вырос. Именно поэтому история в Git — это цепочка, а не список: любой коммит знает своё прошлое. Вторая: идентификатор коммита — это не порядковый номер, а хеш, то есть короткая «подпись», посчитанная из всего содержимого: файлов, автора, даты, сообщения и ссылки на родителя. Отсюда следует правило, которое объяснит потом половину поведения Git: если у коммита изменилось хоть что-нибудь — включая родителя — это уже другой коммит с другим хешем. Мы вернёмся к этому в секции про перебазирование, и там оно окажется ключом ко всему.

Практический побочный эффект: хеш длинный, но в командах почти всегда достаточно первых семи символов — Git сам догадается, о каком коммите речь, пока такое начало уникально в репозитории.

Почему это делает историю надёжной. Раз хеш посчитан в том числе из ссылки на родителя, подменить старый коммит незаметно нельзя: у него сменится хеш, значит, сменится хеш у его ребёнка, и так до самой последней записи. Испортить историю тихо не получится — расхождение сразу видно.

Базовый круг работы

Теперь соберём три места и коммит в один рабочий цикл — тот, который вы будете повторять по несколько раз в день. Цикл короткий: посмотреть состояние, отобрать нужное, сохранить, посмотреть состояние снова. Ниже он показан полностью, вместе с выводом команд: новичку важно не только знать, что набирать, но и узнавать текст, который Git печатает в ответ.

Обратите внимание на роль git status. Это не «служебная» команда для отчётности, а основной инструмент ориентации: она всегда отвечает на вопрос «где я сейчас нахожусь и что у меня незакончено», да ещё и подсказывает следующую команду прямо в тексте. Привычка набирать git status перед и после каждого действия снимает 90% растерянности первых недель — и её стоит завести сразу, а не «когда разберусь».

Второй по важности инструмент — git diff. Он показывает разницу между двумя состояниями: без аргументов — между столом и коробкой, с флагом --staged — между коробкой и последним коммитом. Смотреть на разницу перед коммитом — это самопроверка: примерно половина случайно закоммиченных отладочных строк ловится именно здесь.

Что делать, когда открылся странный текстовый редактор. Если набрать git commit без -m, Git откроет редактор для ввода сообщения — часто это Vim, и выйти из него неочевидно. Спокойно: нажать Esc, набрать :wq и нажать Enter — это «сохранить и выйти». В секции про настройку мы поменяем редактор на удобный.

Что не кладут в репозиторий

Git по умолчанию предлагает сохранить всё, что лежит в папке проекта. Но не всё туда нужно, и некоторые вещи туда нельзя категорически. Есть три группы файлов, которым в истории не место: то, что генерируется автоматически (папки сборки, установленные зависимости), то, что относится к конкретному компьютеру (настройки редактора, служебные файлы операционной системы), и то, что является секретом (пароли, ключи доступа). Для отказа существует специальный файл .gitignore.

Смысл файла .gitignore — список шаблонов имён, которые Git должен перестать замечать. Сам этот файл, в отличие от того, что он скрывает, в репозиторий кладут обязательно: правила игнорирования — общая договорённость команды, а не личная настройка. Самый весомый пункт списка — папка установленных зависимостей: она весит сотни мегабайт, восстанавливается одной командой и меняется при каждом обновлении, то есть даёт огромный объём бессмысленной истории.

Отдельно стоит запомнить главную ловушку: .gitignore не действует задним числом. Если файл уже попал в историю, добавление его имени в список ничего не изменит — Git продолжит следить за ним, потому что уже следит. Файл сначала нужно убрать из-под наблюдения. А если в историю попал секрет, одного удаления мало: он остаётся в старых коммитах и, если репозиторий уже отправлен на хостинг, считается утёкшим. Правильная реакция — не «почистить историю», а сменить сам ключ; подробности того, где секретам место, разобраны на странице про секреты и ключи.

Практический ориентир. Задайте себе один вопрос: «если этот файл удалить, восстановится ли он одной командой?» Если да — почти наверняка его надо игнорировать. Если нет и он одинаков у всех участников — надо коммитить. Если нет и он у каждого свой — ему место в личных настройках, а не в репозитории.

Сообщение коммита

Сообщение коммита — единственное место, где сохраняется причина изменения. Сам код отвечает на вопрос «что сделано»; он и так лежит рядом, его всегда можно прочитать. А вот «зачем» не сохраняется больше нигде: через полгода этого не помнит даже автор. Начинающие пишут сюда что попало — «фикс», «правки», «ещё раз» — и делают это не от лени, а потому что не видели, как эти строки читают потом.

Работающее правило одно: сообщение пишется не для себя сегодняшнего, а для человека, который через год ищет, откуда взялась строка кода, и видит ваш коммит в выводе git blame. Отсюда простая структура: короткая первая строка — что изменилось с точки зрения продукта, а не файла; затем пустая строка; затем несколько предложений о том, почему так, и что было не так раньше. Первая строка короткая не из эстетики — она целиком показывается в списках, в интерфейсе хостинга и в уведомлениях, а длинный хвост обрезается.

В примере упоминается и формальное соглашение — Conventional Commits: договорённость начинать первую строку с типа изменения, например fix:, feat:, docs:. Это не требование Git и не стандарт языка, а соглашение сообщества; полезно оно ровно тем, что типы можно читать машиной — например, автоматически собирать список изменений к версии. Маленькой команде можно спокойно начать без него: разница между «фикс» и внятной фразой на порядок важнее, чем наличие префикса.

Проверка на пригодность. Прочитайте первую строку вслух, подставив в начало «Этот коммит…». Получилось осмысленное предложение — сообщение годится. Получилось «Этот коммит правки» — переписывайте.

Размер коммита

Второй вопрос после «что писать» — «когда сохранять». У новичка обычный ответ: в конце дня, всё сразу, одним коммитом с сообщением «работа за вторник». Это удобно ровно один раз — в момент коммита; вся плата приходит позже, и приходит она к другим людям и к вам же через неделю. Посмотрим, чем именно платят за большой коммит и как разобрать уже намешанное.

Логика такая: коммит — это единица, с которой работают все остальные инструменты. Его целиком показывают на ревью, его целиком откатывают, по нему целиком ищут, когда нужно найти причину поломки. Если внутри одного коммита лежат исправление ошибки, переименование переменных и новая возможность, то отменить исправление, не потеряв остальное, уже нельзя — они склеены навсегда. Хороший размер описывается одной фразой: коммит должен быть про одно законченное изменение, которое можно описать одним предложением без слова «и».

Отсюда же и практическая техника из примера: git add -p позволяет отобрать в коробку не файл целиком, а отдельные его куски. Это спасает ровно в той ситуации, когда вы увлеклись и намешали в одном файле два разных дела — не нужно ничего откатывать, достаточно разложить правки по двум коммитам.

«А если работа не закончена?» Коммит не обязан быть готовой возможностью — он обязан быть связным шагом. Промежуточные коммиты в своей ветке — это нормально и даже полезно: они дают точки, к которым можно вернуться. Прибираются они уже перед вливанием, и как именно — разберём в секциях про перебазирование и запрос на слияние.

Ветка — это указатель, а не копия

Слово «ветка» (branch) звучит внушительно, и почти каждый новичок представляет себе копию проекта: создал ветку — Git где-то скопировал все файлы. Из этого представления растут все дальнейшие страхи: «а не потеряю ли я работу, если переключусь», «а не будет ли тяжело», «а можно ли вообще удалять ветку». Реальность гораздо проще и гораздо скучнее, и после того, как вы её увидите, ветки перестанут пугать навсегда.

Ветка — это файл, внутри которого лежит один хеш. Сорок один байт: сорок символов хеша и перевод строки. Создать ветку — создать такой файл, поэтому это мгновенно независимо от размера проекта. Удалить ветку — удалить файл; сами коммиты при этом остаются на месте, как страницы книги остаются на месте, когда вы вынимаете закладку. А «ветка ушла вперёд» означает буквально: в её файле переписали одну строчку на хеш нового коммита.

Второе понятие из этой же секции — HEAD. Это «закладка, показывающая, какую закладку вы сейчас читаете»: обычно она хранит не хеш, а имя ветки. Когда вы делаете коммит, Git создаёт коммит с текущим в качестве родителя и записывает новый хеш в файл той ветки, на которую смотрит HEAD. Никакой магии в фразе «ветка двигается сама» нет — двигает её именно этот шаг.

Отделённый HEAD. Если переключиться не на ветку, а прямо на коммит, Git скажет «You are in detached HEAD state». Ничего страшного не произошло: вы просто читаете книгу, не держа закладку. Опасно только одно — сделать здесь коммиты и уйти: на них не будет указывать ни одна закладка, и найти их станет трудно. Лечится это заранее: создайте ветку прежде, чем что-то менять.

Ветка от начала до конца

Теория про указатели становится полезной, когда её прикладывают к обычному рабочему дню. Разберём полный путь одной задачи: от «мне дали задачу» до «моя ветка влилась и больше не нужна». Это самая повторяемая последовательность в работе разработчика, её стоит один раз прочитать целиком и потом просто выполнять.

Три момента заслуживают отдельного внимания. Первый: ветку заводят от свежей главной, а не от того, что случайно лежало в рабочей папке — иначе вы с самого начала работаете от устаревшей основы и гарантированно получите лишние расхождения. Второй: перед переключением рабочая папка должна быть чистой; если работа не закончена, её либо коммитят, либо откладывают через git stash. Третий: имя ветки — тоже сообщение. feature/cart-zero-quantity говорит коллеге, чем вы заняты; test2 не говорит ничего.

В примере разбирается и разница между git switch и git checkout. Коротко: checkout — старая команда, которая умеет слишком много разного (и переключать ветки, и восстанавливать файлы), из-за чего её легко применить не по назначению. Ей на смену пришли две узкие команды — switch для веток и restore для файлов. Обе давно не экспериментальные, и новичку лучше начинать сразу с них: меньше шансов случайно затереть свою работу.

Сколько жить ветке. Чем дольше ветка живёт отдельно от главной, тем сильнее она от неё расходится и тем больнее будет сводить. Ориентир для команды любого размера — не больше двух-трёх дней. Если задача явно больше, её надо резать на части, которые можно вливать по отдельности, а не героически вести неделю в одной ветке.

Слияние

Ветка сделана, задача готова — работу надо вернуть в главную ветку. Операция, которая это делает, называется слиянием (merge). Важно понимать, что за одним словом прячутся два довольно разных случая, и по выводу команды они выглядят по-разному. Различать их полезно, потому что дальше от этого зависит вид истории.

Первый случай — перемотка (fast-forward). Он возможен, когда главная ветка с момента вашего ответвления вообще не менялась: тогда «слить» — значит просто передвинуть указатель main вперёд, на ваш последний коммит. Никакого нового коммита не появляется, история остаётся прямой линией. Второй случай — настоящее слияние: и главная, и ваша ветка ушли вперёд каждая по-своему, и Git создаёт особый коммит слияния, у которого два родителя. Именно двойное родительство и делает историю ветвящейся.

Стоит понимать и то, как Git вообще решает, что с чем сводить. Он находит ближайшего общего предка двух веток и сравнивает с ним обе стороны: что изменилось у вас и что изменилось у них. Если стороны трогали разные места — Git объединит правки сам, и никакого участия человека не потребуется. Просить участия он будет только там, где обе стороны правили одни и те же строки, — это и есть конфликт, следующая секция.

Флаг, о который спотыкаются. Флаг --no-ff заставляет Git создавать коммит слияния даже там, где хватило бы перемотки. Смысл — сохранить в истории видимую границу задачи: где она началась и где закончилась. Ценой становится более пёстрый граф. Это вопрос договорённости команды, а не правильности: выберите один вариант и придерживайтесь его.

Конфликт слияния

Конфликт — самое пугающее слово для новичка и при этом одна из самых безобидных ситуаций в Git. Пугает оно потому, что команда прерывается на середине, репозиторий оказывается в непривычном состоянии, а в файлах появляются странные строки из угловых скобок. На деле конфликт — это вежливый отказ угадывать: Git видит, что вы и коллега изменили одни и те же строки по-разному, и не берёт на себя право решить, чей вариант правильный. Разберём весь путь по шагам — от возникновения до завершённого слияния.

Ключ к спокойствию — понять разметку, которую Git вставляет в файл. Строка из семи символов <<<<<<< открывает ваш вариант, строка ======= разделяет варианты, строка >>>>>>> закрывает вариант той стороны, которую вы вливаете. Всё, что между ними, — обычный текст файла. Задача человека — оставить в файле правильный итог и убрать все три служебные строки; при этом «правильный итог» вовсе не обязан быть одним из двух вариантов, часто верным оказывается третий.

Дальше — механика, которая делает процесс предсказуемым. После того как файл приведён в порядок, ему говорят git add: для Git это не «добавить в коммит», а сигнал «здесь я разобрался». Когда разобранными оказываются все конфликтные файлы, слияние завершают командой git commit. И самое важное для новичка: из конфликта всегда есть выход назад — git merge --abort возвращает репозиторий ровно в то состояние, что было до попытки слияния. Ничего не сломано, можно спокойно подумать и попробовать снова.

Как конфликтовать реже. Конфликт — почти всегда следствие организации работы, а не невезения. Короткие ветки, частое подтягивание изменений из главной, договорённость не переформатировать чужие файлы заодно и разделение задач так, чтобы двое не правили один и тот же файл, убирают львиную долю конфликтов ещё до их появления.

Перебазирование

У слияния есть альтернатива с непривычным названием — перебазирование (rebase). Идея простая: вместо того чтобы сводить две расходящиеся линии в одну точку, взять свои коммиты и заново наложить их поверх свежей главной ветки — как будто вы ответвились от неё только что. Результат выглядит опрятнее: история остаётся прямой линией без развилок. Но у этой опрятности есть цена, и её надо понять до того, как начать пользоваться командой.

Самое важное в примере — сравнение хешей до и после. Коммиты после перебазирования выглядят «теми же самыми»: то же сообщение, тот же автор, те же правки. Но хеши у них другие, а значит, по правилу из секции про устройство коммита, это другие коммиты. Механика простая: rebase берёт ваши изменения по одному и заново накладывает их на новую основу, создавая на каждом шаге новый коммит. Родитель сменился — сменился и хеш, и так по всей цепочке. Старые коммиты не исчезают мгновенно, но на них больше никто не ссылается.

Отсюда золотое правило, которое надо просто выучить: не перебазируйте то, что уже отправлено на общий сервер и чем пользуются другие. Пока коммиты живут только у вас в ветке — переписывайте их сколько угодно. Как только на них могут ссылаться коллеги, замена коммитов новыми превращает их работу в мучение: у них старая цепочка, у вас новая, и Git не может понять, какая из них настоящая.

Признакgit mergegit rebase
Что происходит с коммитамиОстаются как есть, хеши не меняютсяЗаменяются новыми, хеши другие
Вид историиС развилками, видны границы задачПрямая линия, читается сверху вниз
Сколько раз разбирать конфликтОдин раз, целикомВозможно, отдельно на каждом коммите
Безопасно для общих ветокДаНет, ломает работу коллег
Кнопка отмены на серединеgit merge --abortgit rebase --abort
Кому подходитЛюбой команде как поведение по умолчаниюСвоя, ещё не отправленная ветка

Разумный компромисс для начинающего. Пользуйтесь rebase только для наведения порядка в собственной ветке до того, как её увидели другие, а в главную вливайте через интерфейс хостинга. Тогда вы получите линейную историю без риска испортить чужую работу.

Удалённый репозиторий

До сих пор всё происходило на одном компьютере. Команда так работать не может: нужно место, куда все складывают сделанное и откуда все забирают чужое. Такое место называется удалённым репозиторием (remote), а живёт оно обычно на хостинге вроде GitHub или GitLab. Технически это точно такой же репозиторий, просто на другой машине; никакого «главного гита» не существует — есть договорённость считать одну копию общей.

Команд для повседневной работы всего четыре, и их различия стоит запомнить точно. clone — скачать репозиторий целиком в первый раз. fetch — забрать с сервера новые коммиты, но ничего не менять в вашей рабочей папке. pull — сделать то же самое и сразу свести с вашей веткой. push — отправить свои коммиты на сервер.

Разница между fetch и pull кажется мелкой, а на практике определяет самочувствие. pull — это fetch плюс автоматическое слияние, то есть он может изменить вашу рабочую папку и даже поставить вас перед конфликтом ровно в тот момент, когда вы к этому не готовы. fetch же безопасен всегда: он только обновляет знание о том, что происходит на сервере, и позволяет сначала посмотреть, а потом решать. Отсюда и объяснение загадочной фразы «ваша ветка отстала на 3 коммита»: Git сравнивает вашу локальную закладку с той, которую он в последний раз видел на сервере.

КомандаЧто делаетМеняет рабочую папкуКогда нужна
git cloneСкачивает репозиторий целиком в новую папкуСоздаёт еёОдин раз, в самом начале
git fetchЗабирает новые коммиты в служебное хранилищеНетКогда хочется посмотреть, что нового, ничем не рискуя
git pullfetch плюс слияние с вашей веткойДаПеред началом работы, на чистой рабочей папке
git pushОтправляет ваши коммиты на серверНетКогда работа готова к тому, чтобы её увидели

Про force push. Рано или поздно Git откажется отправлять ветку и предложит «форсировать». Обычная причина — вы переписали свои коммиты, а на сервере лежат старые. Если ветка ваша личная, безопасный вариант — git push --force-with-lease: он откажется работать, если на сервере появилось что-то, чего вы ещё не видели. Простой --force такой проверки не делает и способен молча стереть чужие коммиты — на общих ветках его не применяют вообще.

Стратегии ветвления

Когда людей больше одного, встаёт вопрос порядка: от чего ответвляться, куда вливать, сколько долгоживущих веток держать. Ответ на него называется стратегией ветвления, и на эту тему написано много страшных схем со стрелками. Полезно знать, что вариантов по сути три, и что для маленькой команды выбор очевиден.

Нулевой вариант — «без стратегии», когда все коммитят прямо в main. Он работает ровно до второго человека, после чего начинается взаимное затирание работы и невозможность что-либо обсудить до попадания в главную. Первый вариант — короткоживущие ветки от главной: одна задача, одна ветка, жизнь два-три дня, вливание через запрос на слияние, после чего ветка удаляется. Второй вариант — GitFlow, схема с несколькими долгоживущими ветками (develop, release, hotfix); он придуман для продуктов, которые выпускаются версиями с длинным циклом подготовки, и для веб-сервиса с частыми выкладками почти всегда оказывается лишним весом.

Практический совет для команды из трёх человек звучит скучно и оттого редко нравится: берите первый вариант и не усложняйте. Одна постоянная ветка main, от неё временные ветки под задачи, вливание через запрос на слияние, ветка после вливания удаляется. Этой схемы хватает командам и в три человека, и в тридцать; переходить на что-то более сложное имеет смысл только тогда, когда вы упрётесь в конкретную проблему и сможете назвать её словами. «Так делают в больших компаниях» — не проблема, а слух.

Правило, которое важнее выбора схемы: главная ветка всегда рабочая. Что бы вы ни выбрали, в main должно лежать состояние, которое можно выложить пользователям прямо сейчас. Всё остальное — детали, о которых можно договориться и передоговориться. Как именно устроена автоматическая выкладка из главной, разбирается на странице про непрерывную интеграцию и доставку, а разделение на тестовый и боевой контуры — на странице про окружения.

Ещё один подход, о котором полезно знать. Trunk-based development — работа очень маленькими порциями почти напрямую в главной, с прятанием незаконченного за переключателями возможностей. Он даёт самую простую историю, но требует зрелой автоматики: без хорошего набора тестов и быстрых проверок это просто «все в main» под красивым названием.

Запрос на слияние

Запрос на слияние — pull request на GitHub, merge request на GitLab — это страница на хостинге вокруг обычного слияния. Технически ничего нового она не делает: тот же git merge, только запущенный по кнопке. Ценность в другом: это точка, где встречаются код, люди и автоматика. Здесь автопроверки говорят, что ничего не сломалось, коллега задаёт вопросы, а вы объясняете своё решение — и всё это остаётся записанным.

Читайте эту структуру как чек-лист: всё, чего в запросе нет, ревьюеру придётся домысливать. Самая полезная и самая часто пустая часть — описание. Ревьюер, открывший запрос без описания, первые десять минут тратит на вопрос «а зачем это вообще», и эти десять минут вы у него отняли. Хорошее описание отвечает на три вопроса: какая была проблема, что вы сделали и как это проверить. Заголовок подчиняется тому же принципу, что и сообщение коммита: понятная фраза для человека не в контексте.

Отдельного разбора заслуживают три кнопки, которыми хостинг предлагает влить запрос. Разница между ними — ровно то, что мы уже разбирали в секциях про слияние и перебазирование, просто без набора команд руками.

Способ вливанияЧто попадёт в главнуюПлюсМинус
Merge commitВсе коммиты ветки плюс коммит слиянияНичего не переписывается, видны границы задачиИстория с развилками, в главной остаётся весь черновой шум
Squash mergeОдин новый коммит вместо всей веткиПрямая история, откат задачи — это откат одного коммитаОтдельные шаги крупной задачи теряются
Rebase mergeВсе коммиты ветки, перенесённые поверх главнойПрямая история и при этом видны все шагиХеши меняются, требует аккуратных коммитов в ветке

Что выбрать команде из трёх человек. Squash merge. Он самый прощающий: коммиты «wip» и «опечатка» просто исчезнут при вливании, и новичку не нужно заранее уметь наводить порядок в своей ветке. Главное правило тут даже не в выборе — выберите один способ на весь репозиторий и включите его по умолчанию в настройках. Смесь трёх стилей в одной истории хуже любого из них по отдельности.

Код-ревью по-человечески

Код-ревью — это когда другой человек читает ваши изменения до того, как они попадут в общую ветку. Звучит как проверка на ошибки, и именно так его обычно и воспринимают: как экзамен, где один умный проверяет другого. От этого недопонимания ревью и портится — превращается в источник обид и в формальность «посмотрел, вроде норм». Полезно знать, что настоящих целей у ревью три, и поиск ошибок среди них не первая.

Первая цель — распространение знания: после ревью про этот код знают минимум два человека, и через полгода, когда автор в отпуске, это спасает команду. Вторая — передача договорённостей: ревью то место, где «как у нас принято» реально переходит от человека к человеку, а не лежит в забытом документе. И только третья — поиск проблем, которые не видит автомат: неверная логика, забытый случай, решение не той задачи.

Из этого следует главное разделение труда, которое стоит завести с первого дня: всё, что можно проверить машиной, человек на ревью проверять не должен. Расстановка пробелов, длина строк, порядок импортов, кавычки, неиспользуемые переменные — это работа линтера и форматтера, и спор о них в комментариях отравляет и автора, и ревьюера. Человеку остаётся то, чего машина не умеет: понятны ли имена, та ли задача решена, что произойдёт при пустом списке и при ошибке сервера.

Вторая половина примера — набор пар «плохой комментарий и хороший на ту же тему». Обобщается он в несколько приёмов, каждый из которых легко применить. Пишите про код, а не про человека: «эта функция делает три вещи», а не «ты написал функцию, которая делает три вещи». Называйте причину и следствие, а не выносите приговор. Задавайте вопрос там, где не уверены, — иногда выясняется, что прав автор. И честно помечайте, что обязательно, а что просто мнение: пометка «не блокирует» экономит часы обсуждений.

Как принимать критику. Второй половине правила учат реже, а она важнее: замечание к коду не является замечанием к вам. Отвечайте по существу, соглашайтесь вслух («да, поправил»), а если не согласны — объясняйте причину, а не молча закрывайте обсуждение. Если разговор идёт третий круг, переносите его в живой разговор на пять минут: текст плохо передаёт интонацию и отлично передаёт раздражение.

Автоматика вокруг ревью

Договорённости, которые держатся только на памяти людей, не держатся. «Мы всегда просим одно одобрение» через месяц превращается в «ну там была срочная правка, я влил сам». Поэтому правила вокруг главной ветки настраивают не на словах, а на хостинге: тогда они выполняются сами, и никому не приходится быть полицейским.

Здесь важно понимать не список галочек, а их порядок по важности. Первое и самое ценное правило — запрет прямой отправки в главную ветку: именно оно превращает запрос на слияние из доброй воли в обязательный шаг. Второе — обязательное одобрение: для команды из двух-четырёх человек одного достаточно, два начинают тормозить работу сильнее, чем ловят ошибок. Третье — обязательные автопроверки: пока линтер и тесты красные, кнопка вливания не нажимается вообще, и спорить с этим невозможно.

Стоит отметить и деталь про хостинг. У GitHub исторически были branch protection rules, они и сейчас работают, но сам GitHub теперь рекомендует вместо них rulesets: на одну ветку могут действовать несколько наборов правил одновременно, а старые правила можно перевести в новый формат. Названия у разных хостингов различаются, набор возможностей примерно один; смотрите на смысл, а не на подпись кнопки.

С чего начать команде из трёх человек. Не включайте всё сразу — иначе вы получите сопротивление вместо порядка. Достаточно трёх вещей: запрет прямой отправки в main, одно обязательное одобрение и обязательный зелёный статус автопроверок. Остальное добавляется, когда становится понятно, чего именно не хватает. Про то, какие проверки вообще имеет смысл вешать на запрос, — следующая страница подраздела.

«Я всё сломал, что делать»

Эту секцию новичок открывает много раз, и написана она именно для этого. Начнём с того, что успокаивает: почти ничто в Git не теряется навсегда. Всё, что было хоть раз закоммичено, лежит в папке .git и достаётся обратно, даже если ветку удалили, историю переписали, а коммит «исчез». По-настоящему потерять можно только то, что вы никогда не коммитили.

Обратите внимание на формат: не «команда и что она делает», а «чего я хочу — какая команда — что после этого произойдёт». В стрессовой ситуации искать нужно именно по желанию, а не по названию команды, которое вы всё равно не помните. Отсюда же берётся понимание разницы между тремя видами git reset: --soft отменяет коммит, но оставляет правки в индексе, --mixed оставляет их в рабочей папке, а --hard стирает совсем — и это единственный из трёх, с которым надо быть осторожным.

Отдельно стоит запомнить одну команду — git reflog. Она показывает журнал того, куда указывал HEAD в последние дни: каждое переключение ветки, каждый коммит, каждый reset. Это и есть та самая страховка, благодаря которой «безвозвратно потерянный» коммит почти всегда находится за минуту. Если однажды у вас всё исчезло — начинайте с неё, а не с паники.

Единственное, чего не вернуть. Изменения, которые не были ни закоммичены, ни отложены через git stash, и которые вы затёрли командой git restore или git reset --hard. Их действительно нет нигде. Отсюда простая привычка, которая стоит дешевле любой страховки: коммитьте часто, даже черновики, — прибраться в своей ветке потом всегда проще, чем восстановить несуществующее.

Начальная настройка Git

Пятнадцать минут один раз — и дальше Git ведёт себя предсказуемо, а не преподносит сюрпризы. Всё, что мы сейчас настроим, пишется в обычный текстовый файл; никакой скрытой магии здесь нет, и любую настройку можно потом посмотреть или отменить.

Первое и обязательное — имя и почта: они попадают в каждый коммит навсегда и меняются потом только переписыванием истории, так что поставьте настоящие ещё до первого коммита. Второе по важности — имя ветки по умолчанию и настройка перевода строк: без неё участники на Windows и на macOS начинают видеть «изменения» в файлах, которых никто не трогал, потому что системы записывают конец строки по-разному. Третье — редактор для сообщений коммита, чтобы не воевать с Vim.

Полезно понимать уровни настроек: --global действует на все ваши репозитории и лежит в домашней папке, --local — только на текущий и лежит внутри .git, а команда без флага показывает то, что действует прямо сейчас, с учётом обоих. Это пригодится, например, если рабочая почта отличается от личной: глобально ставите одну, а в рабочем репозитории локально переопределяете.

Что стоит добавить сразу после. Псевдонимы для длинных команд и настройку способа подтягивания изменений (слияние или перебазирование), чтобы git pull всегда вёл себя одинаково у всех в команде. Всё остальное добавляйте по мере того, как надоест печатать длинное, — заранее настраивать то, чем вы ещё не пользуетесь, смысла нет.

Коротко

  • Система контроля версий хранит причину, а не только состояние. Копирование папок сохраняет файлы, но теряет ответ на вопрос «зачем это было сделано».
  • Мест три, а не два. Рабочая папка — стол, индекс — открытая коробка, репозиторий — отправленная посылка.
  • git add ничего не сохраняет. Он только кладёт в коробку копию того, что лежало на столе в этот момент. Сохраняет только git commit.
  • Коммит — снимок, а не список правок. В него входят файлы, автор, дата, сообщение и ссылка на родителя.
  • Хеш посчитан из содержимого. Изменилось что угодно, включая родителя, — это уже другой коммит.
  • git status — не отчёт, а компас. Он всегда отвечает «где я и что незакончено», и подсказывает следующую команду.
  • Секретам и сгенерированному в репозитории не место. А если ключ туда всё-таки попал, его меняют, а не «чистят историю».
  • Сообщение коммита пишется для чужого человека через год. Первая строка — что изменилось для продукта, дальше — почему так.
  • Один коммит — одно изменение. Если в описание просится слово «и», перед вами два коммита.
  • Ветка — файл на 41 байт с хешем внутри. Создание мгновенно, удаление ничего не стирает, коммиты остаются на месте.
  • HEAD указывает на имя ветки. Поэтому новый коммит двигает вперёд именно ту закладку, на которой вы стоите.
  • Слияние бывает двух видов. Перемотка просто двигает указатель; настоящее слияние создаёт коммит с двумя родителями.
  • Конфликт — не поломка, а вопрос. Git отказывается угадывать, чей вариант верен; у вас всегда есть git merge --abort.
  • Перебазирование создаёт новые коммиты. Не делайте его с тем, что уже отправлено на сервер и чем пользуются другие.
  • fetch безопасен, pull меняет рабочую папку. Сначала посмотреть, потом сводить — рабочая привычка на каждый день.
  • Короткие ветки от главной подходят почти всем. Главная всегда в рабочем состоянии — это правило важнее выбора схемы.
  • Запрос на слияние — место, где вы объясняете себя. Маленький и с честным описанием проходит за час, большой и пустой висит неделю.
  • Стиль проверяет машина, смысл — человек. Спор о пробелах в комментариях ревью означает, что автоматика не настроена.
  • Правила пишут в настройках хостинга, а не в чате. Запрет прямой отправки, одно одобрение, зелёные проверки — этого достаточно для старта.
  • Почти ничто не теряется. git reflog помнит, куда указывал HEAD; невозвратно теряется только незакоммиченное.
