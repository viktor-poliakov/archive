Метаданные

Иногда декоратору не нужно менять поведение — ему нужно просто оставить заметку: «это поле обязательное», «этот столбец — текстовый», «этот метод доступен только админам». А потом другой код собирает все заметки и что-то с ними делает: проверяет форму, строит таблицу в базе, раздаёт права. Такие заметки называются метаданными. Представьте склад: на коробках расклеены бирки — «хрупкое», «верх», «партия №7». Сама коробка от бирки не меняется, но кладовщик по биркам знает, что делать. У стандартных декораторов для таких бирок есть общий «блокнот» — context.metadata. Разберём, как в него писать и как читать. Если это ваша первая страница про декораторы, начните с основ.

Общий блокнот класса

context.metadata — это обычный объект-«блокнот», один на класс. Все декораторы этого класса пишут в один и тот же блокнот, а снаружи его можно прочитать через Класс[Symbol.metadata]:

Две первые строчки — не часть идеи, а плата за новизну. Symbol.metadata настолько свежий, что его пока нет ни в браузерах, ни в Node, и TypeScript по умолчанию про него тоже не знает. Уберите строку с <reference lib="esnext.decorators" /> — и получите три ошибки подряд: 'context.metadata' is possibly 'undefined', Element implicitly has an 'any' type… и Property 'metadata' does not exist on type 'SymbolConstructor'. Уберите полифилл — код скомпилируется, но упадёт при запуске с TypeError: Cannot set properties of undefined. В настоящем проекте вместо строки с reference пишут "lib": ["ESNext"] в tsconfig.json; подробный разбор — ниже, в разделе «Что нужно для Symbol.metadata». В остальных примерах страницы обе строчки подразумеваются и не повторяются.

Ключевая мысль: блокнот общий. Сколько бы декораторов ни сработало на разных полях и методах класса, все они дописывают в один и тот же объект metadata. Поэтому декоратор одного поля может «накапливать» список вместе с декораторами других полей — чем мы сейчас и воспользуемся.

Практика 1: обязательные поля формы

Классическая задача — проверить, что обязательные поля формы заполнены. Разложим её на две роли: декоратор @required только записывает в блокнот имя обязательного поля, а отдельная функция validate потом читает блокнот и проверяет. Что нужно для Symbol.metadata

Пара технических деталей, без которых ничего из написанного выше не запустится. Symbol.metadata — это новый системный символ, под которым язык хранит блокнот на классе. Он настолько свежий, что его пока нет ни в браузерах, ни в Node. Поэтому нужны две независимые вещи: типы для компилятора и полифилл для запуска. И есть ловушка: последняя из трёх ошибок советует сменить lib на esnext, а рука тянется поставить target: ESNext — ошибки пропадут, но код перестанет запускаться вовсе.

Что забыли Когда это вылезет Что вы увидите
Подключить типы через lib Сразу, при проверке типов ❌ три ошибки, последняя прямо советует сменить lib на esnext
Поставили target: ESNext вместо lib При запуске, ещё до выполнения кода ❌ SyntaxError: Invalid or unexpected token на строке с декоратором
Полифилл При запуске, на первом же декораторе ❌ TypeError: Cannot set properties of undefined
Записать хоть что-нибудь в блокнот При чтении снаружи ❌ Класс[Symbol.metadata] равен undefined
Ничего не забыли — ✅ объект с вашими заметками

Две мелочи, которые удивляют при первом запуске. Во-первых, блокнот появляется, только если у класса есть хоть один декоратор, который в него что-то записал: у класса без записей Класс[Symbol.metadata] так и останется undefined, и это нормально. Во-вторых, объект метаданных создаётся без прототипа, поэтому в консоли Node он печатается как [Object: null prototype] { … } — данные в нём обычные, просто у него нет унаследованных методов вроде hasOwnProperty.

Метаданные в старом мире: reflect-metadata

Здесь важно не запутаться, потому что вы наверняка встретите совсем другой механизм. В Angular и NestJS метаданные сделаны не через Symbol.metadata, а через библиотеку reflect-metadata и флаг emitDecoratorMetadata. С этим флагом компилятор сам записывает типы параметров конструктора, а контейнер внедрения зависимостей (DI) их читает и понимает, какие объекты создать и подставить:

Не путайте два механизма. Стандартные декораторы хранят заметки в context.metadata и достают через Symbol.metadata. Старые (Angular/NestJS) — в reflect-metadata, достают через Reflect.getMetadata(...), и главная их фишка — автоматически сохранённые типы (design:type, design:paramtypes), чего у стандартных пока нет. Это два разных мира, живущих под разными флагами компилятора.

Коротко

  • Метаданные — это заметки-«бирки», которые декоратор оставляет о классе и его частях, чтобы другой код прочитал их позже.
  • context.metadata — общий блокнот, один на класс. Все декораторы класса пишут в него; снаружи читают через Класс[Symbol.metadata].
  • Типичный сценарий: декораторы только записывают (обязательность поля, тип столбца), а отдельная функция потом читает и действует (валидация, генерация SQL).
  • Универсальность: код-читатель не знает конкретных классов заранее — он работает с любым, у кого есть нужные заметки.
  • Технические условия: может понадобиться полифилл Symbol.metadata и современный lib (ESNext) в tsconfig.json.
  • Старый мир — отдельно: Angular и NestJS используют reflect-metadata и emitDecoratorMetadata (сохранение типов для DI), а не Symbol.metadata. Механизмы разные.
