Импорт и экспорт типов

Представьте, что ваш модуль — это завод. Импортировать значение (функцию, переменную, класс) — всё равно что привезти на завод настоящий станок: он тяжёлый, занимает место в собранном коде и может «шуметь» — выполнять что-то уже при включении. А импортировать тип — это как получить чертёж: по нему сверяются во время сборки, а потом чертёж выбрасывают. В готовый продукт он не попадает вовсе. Типы в TypeScript живут только на этапе компиляции и полностью стираются из итогового JavaScript. На этой странице разберёмся, как экспортировать и импортировать типы и зачем придумали особые слова import type и export type.

Типы экспортируются как обычные значения

Начнём с хорошей новости: чтобы «поделиться» типом с другим файлом, ничего особенного делать не нужно. interface и type экспортируют тем же словом export, что и функции с переменными. А импортируют так же — фигурные скобки и имя. Пусть один файл описывает пользователя:

Проблема: обычный импорт может «застрять» в собранном коде

Вот в чём загвоздка. Компилятор видит строку import { User } from './user' и должен решить: User — это тип (тогда строку надо стереть) или значение (тогда её надо оставить)? Обычно он справляется. Но в некоторых режимах сборки — особенно когда файлы компилируются по одному, в изоляции (бандлеры вроде esbuild, опция isolatedModules) — компилятор смотрит только на текущий файл и не знает, чем окажется User в соседнем. На всякий случай он оставляет импорт в готовом .js.

Само по себе это было бы полбеды. Но импорт файла запускает весь код верхнего уровня этого файла — его побочные эффекты. Представим модуль-логгер, который что-то делает уже при загрузке:

Мы притащили на завод целый станок и включили его — ради одного лишь чертежа. Это и лишний вес в бандле, и неожиданные побочные эффекты, и потенциальные проблемы с циклическими импортами.

Решение: import type и export type

Чтобы снять всякую двусмысленность, придумали отдельную запись — import type. Она говорит компилятору прямо и без догадок: «это только тип, в рантайме удали его целиком». Такой импорт гарантированно исчезает из собранного JavaScript — вместе со всеми побочными эффектами модуля, если больше из него ничего не берут.

Симметричная запись есть и для экспорта — export type. Она пригождается, когда модуль работает «фасадом»: собирает типы из разных мест и пробрасывает их наружу единым списком. export type тоже полностью стирается из рантайма:

Простое правило. Пишете import type или export type — вы обещаете компилятору, что за этими скобками нет ни одного значения, только типы. Компилятор ловит вас на слове: если вы попробуете тем же импортом затащить настоящую функцию, будет ошибка. Так запись остаётся честной.

Встроенный модификатор type в одной строке

А что, если из одного модуля нужны и тип, и значение сразу? Делить их на два отдельных импорта — import type { User } и import { createUser } — можно, но громоздко. Поэтому появилась третья форма: пометить словом type отдельное имя прямо внутри фигурных скобок. Помеченное — тип (сотрётся), остальное — значение (останется).

Разница тонкая, но важная. import type { ... } (слово type перед скобкой) означает, что вся строка — только типы. А import { type User, createUser } (слово type внутри скобок, перед конкретным именем) помечает лишь одно имя, оставляя соседей обычными значениями. Вторая форма — самая удобная в повседневном коде, когда тип и функция лежат в одном модуле.

Зачем это на практике

Может показаться, что import type — мелочь для педантов. На деле у него несколько вполне ощутимых выгод:

  • Чистый бандл и точный tree-shaking. Импорты-типы гарантированно исчезают, и сборщику проще выкидывать всё лишнее. В готовый JavaScript не попадает ни байта «чертежей».
  • Нет случайных побочных эффектов. Взяли из модуля только тип — значит его код при загрузке точно не выполнится. Никаких сюрпризов вроде «logger.ts загрузился!».
  • Меньше проблем с циклическими импортами. Если два модуля ссылаются друг на друга только типами, то после стирания импортов цикл в рантайме исчезает сам собой.
  • Совместимость со строгими сборщиками. Режимы isolatedModules и verbatimModuleSyntax могут требовать import type — без него будет ошибка компиляции.

Про последний пункт стоит сказать отдельно. Опция verbatimModuleSyntax (её всё чаще включают в новых проектах) переводится как «дословный синтаксис модулей». Смысл простой: компилятор больше не угадывает сам, какой импорт стереть, а какой оставить, — он делает буквально то, что написано. Значение оставляет, import type стирает. А раз он не угадывает — помечать типы словом type обязаны вы сами.

Коротко

  • Типы экспортируются и импортируются как значения. export interface User { … } → import { User } from './user'. Внешне импорт типа не отличить от импорта функции.
  • Типы стираются из рантайма. Значение — это «станок» (остаётся в собранном JS и может «шуметь» побочными эффектами), тип — это «чертёж» (исчезает после сборки).
  • Обычный import для типа рискует «застрять» в .js при изоляции файлов (isolatedModules, бандлеры) и затащить лишний код с его побочными эффектами.
  • import type { User } — «это только тип, в рантайме удали полностью». export type { User } — реэкспорт лишь типа. Обе записи гарантированно исчезают из JS.
  • Встроенная пометка import { type User, createUser } помечает одно имя как тип, оставляя соседнее значение обычным — удобно, когда тип и функция в одном модуле.
  • verbatimModuleSyntax — «пиши импорты буквально»: компилятор ничего не угадывает, и помечать типы словом type нужно самому, иначе ошибка.
