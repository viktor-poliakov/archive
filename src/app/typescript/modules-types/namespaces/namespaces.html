Пространства имён

Пространство имён (namespace) — это подписанный ящик, в который складывают родственные вещи, чтобы они держались вместе и не путались с чужими. Представьте кладовку без полок: все банки, коробки и инструменты свалены в одну кучу, и две банки с одинаковой этикеткой «САХАР» невозможно различить. Ящик с подписью спасает: положили нужное внутрь, подписали «КУХНЯ» — и теперь достаём через КУХНЯ.сахар, не путая с гаражным. Именно это и делает namespace для кода. Но есть важная новость: современный JavaScript выдаёт каждому файлу собственный ящик автоматически — это модули. Поэтому заводить ящики вручную сегодня почти не нужно, и namespace в новом коде считается легаси. Разберёмся, что это, откуда взялось и где ещё уместно.

Что такое namespace

Синтаксис простой: слово namespace, имя ящика и фигурные скобки, внутри которых живёт содержимое — типы, функции, переменные. Ключевой момент: наружу видно только то, что помечено словом export. Всё остальное спрятано внутри, как вещи на дне закрытого ящика.

Снаружи к «публичным» членам обращаются через имя ящика и точку: Geometry.Point, Geometry.area. Само имя Geometry — это как надпись на боку ящика; по ней вы находите нужную полку. А то, что не помечено export (в примере — version), остаётся приватным: снаружи его не достать, компилятор об этом честно скажет.

Приватные члены — не бесполезны: ими пользуется код внутри самого ящика. Это удобно для вспомогательных функций, которые не хочется показывать наружу:

Откуда это взялось: немного истории

Чтобы понять, зачем namespace вообще придумали, вернёмся в прошлое — во времена до ES-модулей. Тогда файлы подключали в HTML тегами <script>, и у них не было никакой изоляции: все переменные верхнего уровня из всех файлов сваливались в одну общую (глобальную) область. Файлы «видели» друг друга напрямую — но и мешали друг другу: две переменные с одинаковым именем в разных файлах затирали одна другую.

Это и есть коллизия имён — главная головная боль той эпохи. Чем больше файлов, тем выше шанс, что где-то два человека назвали переменную data, utils или config, и они молча перезаписали друг друга. Тогда namespace (в те годы их называли внутренними модулями, internal modules) и предложили как лекарство: сложить каждый набор кода в свой ящик, а глобальными оставить только имена самих ящиков.

Суть исторической роли. namespace появился как способ навести порядок в общей глобальной свалке: вместо десятков глобальных имён — несколько ящиков-пространств. Для своего времени это был большой шаг вперёд. Но сама проблема — «всё общее и глобальное» — исчезла, когда в язык добавили настоящие модули.

Современная позиция: используйте ES-модули

Сформулируем прямо и без оговорок: для нового кода берите ES-модули, а не namespace. Модуль — это просто файл с import/export. Каждый такой файл язык изолирует автоматически: всё, что вы в нём объявили, приватно для файла, пока вы явно не напишете export. Тот самый «ящик», который раньше приходилось заводить руками через namespace, теперь выдаётся бесплатно на каждый файл.

Почему модули победили и рекомендуются везде? Причин несколько, и все практические:

  • Инкапсуляция «из коробки» — граница ящика совпадает с границей файла, отдельная обёртка не нужна.
  • Ленивая загрузка — модуль можно подгрузить по требованию через динамический import(); namespace так не умеет.
  • Tree-shaking — сборщик выкидывает неиспользованные экспорты и уменьшает бандл; содержимое namespace труднее «встряхнуть».
  • Работа со сборщиками и экосистемой — весь современный инструментарий (Vite, webpack, esbuild, npm-пакеты) построен вокруг модулей.

Есть и важное правило гигиены: не смешивайте модули и namespace для организации кода. Как только в файле появился import или export, он уже стал модулем — оборачивать его содержимое ещё и в namespace лишнее и только запутывает пользователя двойными путями.

Правило. Файл-модуль сам по себе — уже пространство имён: его имя задаёт путь импорта, а export решает, что видно. Второй ящик поверх модуля не добавляет пользы. Про сами модули — страницы Основы модулей и Импорт и экспорт типов.

Где namespace ещё уместен

«Легаси» не значит «запрещено». Есть два случая, где namespace и сегодня на своём месте.

1. Глобальные типы в .d.ts

Некоторые старые библиотеки не являются модулями: их подключают тегом <script>, и они кладут себя в глобальную переменную (например, window.MyLib). Чтобы описать типы такой библиотеки, её сгруппировывают в глобальном файле объявлений .d.ts — и namespace тут ровно к месту: он моделирует «объект-контейнер», который в рантайме доступен глобально.

2. Слияние объявлений (function + namespace)

Второй случай — паттерн слияния объявлений: функция и namespace с одним и тем же именем сливаются в единую сущность. Так к вызываемой функции «приклеивают» статические свойства и вспомогательные функции.

Не путать с declare module '…'. Запись declare module 'имя' — это про описание или дополнение внешних модулей, совсем другая тема, а не про namespace. Детали — на страницах Слияние объявлений и Нюансы и подводные камни.

Вложенность и export внутри

Ящики можно вкладывать друг в друга — как папки внутри папок. Правило видимости то же на каждом уровне: чтобы вложенный ящик или его член был доступен снаружи, его тоже нужно пометить export. Обращение идёт по цепочке имён через точку: App.Models.User.

Длинные цепочки вроде App.Models.User утомляют. Их сокращают import-псевдонимом — это специальная запись TypeScript import Имя = Путь.К.Ящику (не путать с ES-импортом из файла): она заводит короткий локальный синоним для длинного пути.

namespace против ES-модуля: сравнение

Свести всё воедино проще всего таблицей. По каждому пункту, важному для реального проекта, модуль выигрывает — поэтому именно он рекомендован для нового кода.

Критерий namespace ES-модуль (файл)
Инкапсуляция ❌ ящик заводят вручную ✅ каждый файл изолирован сам
Ленивая загрузка (по требованию) ❌ нет ✅ динамический import()
Tree-shaking (выброс лишнего) ❌ плохо поддаётся ✅ да, сборщик режет неиспользованное
Сборщики и экосистема npm ❌ не рассчитаны на него ✅ построены вокруг модулей
Актуальность для нового кода ❌ легаси ✅ стандарт по умолчанию

Коротко

  • namespace — «подписанный ящик»: группирует родственные типы и код под одним именем. Снаружи видно только помеченное export, доступ — через Имя.член.
  • История: до ES-модулей все файлы сливались в одну глобальную область и коллизии имён были обычным делом; namespace (тогда — «внутренние модули») наводил в ней порядок.
  • Сегодня для нового кода — ES-модули, не namespace. Файл = модуль = свой ящик автоматически. Модули дают инкапсуляцию, ленивую загрузку, tree-shaking и работают со сборщиками.
  • Не смешивайте модули и namespace: файл с import/export уже пространство имён, второй ящик поверх лишний.
  • Где ещё уместен: в глобальных .d.ts для старых библиотек-глобалей и в слиянии объявлений (function + namespace).
  • Не путать namespace с declare module '…' — последнее про описание и дополнение внешних модулей, отдельная тема.
