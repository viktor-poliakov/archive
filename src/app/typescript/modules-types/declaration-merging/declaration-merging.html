Слияние объявлений

Представьте: два сотрудника отдела кадров описывают одного и того же человека. Первый записал «рост 180, глаза карие», второй — «водит машину, знает английский». Вы не заводите две карточки — вы складываете оба описания в одно, более полное досье. Ровно это делает TypeScript со слиянием объявлений (declaration merging): если он встречает несколько объявлений с одним и тем же именем, он не ругается на повтор, а объединяет их в одно целое. Другой образ: вы не заводите вторую папку с тем же названием, а подшиваете новые листы в уже существующую папку.

Базовый случай: два interface с одним именем

Начнём с самого частого и самого полезного вида слияния — двух интерфейсов. Объявим interface Box дважды: в первом объявлении зададим ширину, во втором — высоту. TypeScript не считает это ошибкой. Он берёт поля из всех объявлений с именем Box и складывает их в один интерфейс.

Результат такой, будто вы с самого начала написали оба поля в одном интерфейсе. Поэтому переменная типа Box теперь обязана иметь и width, и height — попытка создать Box только с шириной завершится ошибкой TS2741.

Важно, что объявления не обязаны стоять рядом. Их можно разнести по файлу (а при дополнении глобальных типов — и по разным файлам проекта): TypeScript всё равно найдёт всех «однофамильцев» и соберёт в одно досье.

Что можно и нельзя при слиянии интерфейсов. Складывать разные поля — можно. А вот объявить одно и то же поле с разными типами нельзя: width: number в одном объявлении и width: string в другом дадут ошибку TS2717 «Subsequent property declarations must have the same type». Слияние добавляет поля, но не позволяет им противоречить друг другу.

Контраст: type-псевдонимы НЕ сливаются

А теперь главное отличие, которое надо запомнить накрепко: сливаются интерфейсы, но не type-псевдонимы. Если объявить type с одним именем дважды, TypeScript расценит это не как «добавить листов», а как «завести вторую папку с тем же названием» — и запретит повтор ошибкой Duplicate identifier.

Логика простая: имя, занятое type, считается занятым окончательно — второй раз его объявить нельзя. Интерфейс же остаётся «открытым» для новых объявлений (об этом — в предпоследнем разделе). Хотите с type получить объединение полей — соединяйте типы вручную через пересечение &, как показано в конце примера выше.

Ещё одно отличие interface от type. Способность сливаться — одно из практических различий между ними. Полное сравнение с рекомендациями, что и когда выбирать, — на странице Интерфейс или тип. А расширение интерфейса «в лоб» через extends разобрано в Расширение интерфейсов.

Другие виды слияния (кратко)

Слияние — механизм не только для интерфейсов. Под одним именем могут ужиться и объявления разного рода. Самый наглядный пример — функция плюс namespace: к функции «прикрепляют» статическое поле. В JavaScript функциям давно можно дописывать свойства (greet.version = '1.0'), и слияние даёт этому типобезопасную запись.

После слияния имя greet — это одновременно и вызываемая функция, и «папка» со свойством version. Так же между собой сливаются namespace + namespace, interface + namespace, enum + namespace — все они частные случаи одного правила: «несколько объявлений с одним именем становятся одним целым». Глубоко в эти комбинации сейчас не погружаемся; про сами пространства имён есть отдельная страница Пространства имён.

Главная польза: дополнять чужие и глобальные типы

Зачем всё это на практике? Ответ: слияние — единственный штатный способ дополнить тип, который вам не принадлежит и который нельзя отредактировать напрямую. Тип из стандартной библиотеки (Window), тип из чужой библиотеки (Request в Express) — открыть их файл и дописать поле вы не можете. Но можете подшить своё объявление к существующему интерфейсу. Такой приём называют augmentation (дополнение).

Глобальное дополнение: declare global

Допустим, вы кладёте свой объект приложения прямо в глобальный window.myApp. TypeScript про такое поле ничего не знает — тип Window описан в стандартной библиотеке. Добавим поле сами, дополнив интерфейс Window внутри блока declare global.

После этого обращения к window.myApp становятся типобезопасными: TypeScript знает форму вашего поля, подсказывает методы и ловит опечатки. Обратите внимание на последнюю строку — export {};. Она делает файл модулем, а это обязательное условие для declare global: дополнять глобальную область можно только из модуля. Подробнее про само ключевое слово — на странице Ключевое слово declare.

Дополнение модуля: declare module

Похожая история с типами из сторонних библиотек. Частый пример из мира Node.js: во фреймворке Express у объекта запроса Request нет поля user, а вам нужно класть туда авторизованного пользователя. Открыть исходники Express и дописать поле нельзя — зато можно дополнить модуль: объявить блок declare module 'express' и добавить в его интерфейс Request своё поле.

Два условия, без которых дополнение модуля не сработает:

  • Файл должен быть модулем — то есть содержать хотя бы один import или export. В примере роль «сделать файл модулем» играет строка import 'express';. Без импорта/экспорта declare module 'express' будет понят иначе (как объявление нового окружающего модуля), и слияния не произойдёт.
  • Имя в declare module '…' — точно как при импорте библиотеки. Пишете import ... from 'express' — значит и дополнять надо declare module 'express', символ в символ. Ошиблись в имени — TypeScript решит, что это другой, новый модуль, и ваше поле не приклеится к настоящему Request.

Куда это писать. Такие дополнения обычно кладут в отдельный файл объявлений — см. Файлы объявлений .d.ts. А как вообще подключаются типы чужих библиотек (пакеты @types) — на странице Типы библиотек @types.

Почему именно через interface

Осталось объяснить, почему дополняют всегда именно интерфейсы, а не type. Причина — та самая, с которой мы столкнулись во втором разделе: интерфейс «открыт» для новых объявлений, а type «закрыт». К интерфейсу всегда можно добавить ещё одно объявление, и поля сольются; имя, занятое type, повторно объявить нельзя.

Поэтому библиотеки, которые хотят разрешить пользователям себя расширять, специально публикуют интерфейсы — как оставленную дверцу. Express объявляет Request интерфейсом именно затем, чтобы вы могли дополнить его своими полями, не форкая библиотеку.

Вывод. «Открытость» интерфейса — не случайная деталь, а сознательный приём. Если проектируете тип, который другим захочется расширять (точку расширения, конфиг плагина, объект контекста), делайте его interface, а не type — тогда его можно будет дополнить через слияние.

Коротко

  • Слияние объявлений — TypeScript объединяет несколько объявлений с одним именем в одно целое. Образ: подшить новые листы в существующую папку, а не завести вторую.
  • Два interface с одним именем складывают поля. interface Box { width } + interface Box { height } = Box с обоими полями. Одно поле с конфликтующими типами — ошибка.
  • type не сливается. Повторный type X — ошибка Duplicate identifier 'X'. Это одно из отличий интерфейса от типа; объединять type надо вручную через &.
  • Сливаются и другие пары — функция + namespace (статическое поле на функции), namespace + namespace, interface + namespace, enum + namespace.
  • Главная польза — дополнять чужие типы. Глобально через declare global { interface Window { … } }, модуль библиотеки — через declare module 'lib' { interface … }.
  • Условия дополнения модуля: файл должен быть модулем (иметь import/export), а имя в declare module — точно как в импорте.
  • Дополняют интерфейсы, потому что интерфейс «открыт» для расширения; библиотеки для того и публикуют интерфейсы-точки расширения.
