Нюансы и подводные камни

Модули и типы — это как разные отделы большого склада. Каждый файл-модуль — отдельная комната со своей дверью: чтобы что-то взять из соседней, нужно официально её «импортировать». А описания типов (declare, .d.ts) — это таблички и инструкции на стенах: они говорят, что где лежит, но сами ничего не кладут на полку. Почти все грабли этого раздела растут из путаницы между «настоящим кодом, который выполняется» и «описанием, которое живёт только в компиляторе». Здесь собраны самые частые ловушки — с примером, объяснением почему так и как сделать правильно. Если базовые вещи ещё в новинку, начните со страниц Импорт и экспорт типов и Ключевое слово declare.

1. Забыли import type — импорт остаётся в рантайме

Когда вам из модуля нужен только тип (для аннотации : User), а вы пишете обычный import { User }, компилятор оставляет этот импорт в собранном JavaScript. Это значит, что модуль реально загрузится и выполнит весь свой код — включая побочные эффекты, которые вам вовсе не нужны.

А при строгой опции verbatimModuleSyntax забытый import type — это уже не «лишний вес», а прямая ошибка компиляции (TS1484): в этом режиме компилятор ничего не «додумывает» и обязан по одному файлу понять судьбу каждого импорта, а User, ввезённый обычным import, обязан быть значением — но это только тип.

Как правильно. Чисто-типовые импорты помечайте import type { User }. Если из модуля берёте и тип, и значение — помечайте только тип прямо в списке: import { saveUser, type User }. Подробнее — на странице Импорт и экспорт типов.

2. declare — это обещание БЕЗ проверки

declare говорит компилятору: «поверь, снаружи существует вот такая переменная (функция, тип)». Это только обещание — ровно как приведение as. Компилятор ничего не проверяет: если описанного на деле нет, он всё равно спокойно пропустит код.

Как правильно. Во-первых, убедитесь, что описанное действительно подключено (тег на месте, имя совпадает буква в букву). Во-вторых, если существование под вопросом — не обещайте, а проверяйте в рантайме: опишите значение как «может отсутствовать» и смотрите перед вызовом. 3. Случайный import/export превращает глобальный .d.ts в модуль

В TypeScript действует железное правило: как только в файле появляется хоть один верхнеуровневый import или export, файл становится модулем. А всё, что объявлено в модуле, — локально: снаружи это видно только через импорт. Для обычного кода это хорошо. Но для глобального файла объявлений (globals.d.ts), который специально написан, чтобы раздавать типы всему приложению, это катастрофа: одна случайная строчка import — и все глобальные объявления «пропадают».

4. type НЕ сливается, а interface — сливается

Соблазн: расширить существующий тип, объявив его ещё раз с новыми полями — как будто поля «сложатся». С type это не работает: два объявления с одним именем компилятор считает конфликтом.

А вот interface с тем же именем не конфликтуют, а сливаются — это и называется слиянием объявлений (declaration merging). Поля из всех объявлений складываются в один интерфейс:

Именно на этом свойстве держится расширение чужих (библиотечных) типов — augmentation. Дополнить библиотечный type повторным объявлением нельзя (получите Duplicate identifier), а interface (и namespace) — можно.

Как правильно. Для расширения существующих типов используйте interface + module augmentation. Собственные типы, которые кто-то будет дополнять, тоже лучше объявлять как interface. Разбор темы — Слияние объявлений и interface против type.

5. Module augmentation «молча» не срабатывает

Вы написали declare module '…' { … }, чтобы добавить поле в библиотечный тип, — а оно не появляется, и ошибок тоже нет. Почти всегда причина одна из двух: файл не является модулем или имя модуля не совпадает с тем, что реально импортируют.

Первая причина: чтобы declare module дополнял существующий модуль (а не описывал новый с нуля), файл сам должен быть модулем — то есть содержать хотя бы один import или export. Вторая причина коварнее: строка в declare module 'express' должна совпадать с путём импорта буква в букву. 'Express', 'express/index' или лишний слэш — это, с точки зрения компилятора, другой модуль, и дополнение уходит в пустоту.

Как правильно. Файл-дополнение должен иметь import/export (подойдёт хоть export {}; или import 'express';). Имя в declare module '…' пишите точно так же, как в import. Детали — Слияние объявлений и Типы библиотек @types.

6. @types рассинхронизированы с версией библиотеки

Типы для библиотеки часто ставят отдельным пакетом @types/имя. Беда в том, что версия типов и версия самой библиотеки — это два независимых пакета. Если они разъехались, типы начинают врать: описывают API, которого в вашей установленной версии нет (или наоборот, не знают про новый метод).

Обе стороны неприятны. Если @types новее библиотеки — компилятор разрешит вызвать метод, которого в рантайме ещё нет (упадёт при запуске). Если @types старее — компилятор запретит реально существующий метод, и вы будете спорить с редактором на пустом месте.

Как правильно. Держите версии согласованными — подбирайте @types под ту же мажорную/минорную версию библиотеки. А если библиотека уже поставляет свои типы (в ней есть .d.ts и поле "types" в package.json), отдельный @types не нужен — он лишний и может конфликтовать. Подробнее — Типы библиотек @types.

7. namespace для организации кода в проекте на модулях

Раньше, до появления ES-модулей, код группировали в namespace — «пространства имён», доступ к которым идёт через точку (Utils.formatDate). В современном проекте, где каждый файл и так модуль, использовать namespace для организации своего кода — антипаттерн: он дублирует роль модулей, путает и, главное, мешает tree-shaking (удалению неиспользуемого кода из бандла).

Проблема в том, что namespace — это единый объект: сборщик не может понять, какие его части используются, а какие нет, и тащит в бандл всё целиком. Модули же экспортируют функции по отдельности, и сборщик спокойно выкидывает то, что нигде не импортировано.

Как правильно. В прикладном коде организуйте всё модулями (файл = модуль, точечные export/import). Законное место namespace сегодня — старые .d.ts и глобальные типы, а не структура вашего приложения. Подробнее — Пространства имён.

8. Легаси export = и import x = require(…)

Помимо ES-синтаксиса (import/export) в TypeScript есть старый синтаксис из мира CommonJS: export = для экспорта «всего модуля одним значением» и парный ему import x = require(…). Его ещё встречают в старом коде и в некоторых .d.ts, но в новом коде мешать его с ES-синтаксисом не стоит.

Эти две системы плохо уживаются в одном файле: при сборке в ES-модули import x = require(…) вызывает ошибку компиляции, потому что это принципиально разные модели.

Как правильно. Современный код пишите на ES-синтаксисе (import/export, export default). Если нужно подружиться со старой библиотекой на module.exports = …, включите опцию esModuleInterop — тогда обычный default-импорт корректно свяжется с CommonJS-экспортом, и import = require не понадобится. Про импорт/экспорт целиком — Импорт и экспорт типов.

Сводка: частая ошибка → как правильно

Частая ошибка Как правильно
Обычный import { T } для чисто-типового импорта import type { T } (или import { type T })
declare и надежда, что «оно точно есть» Убедиться, что подключено; внешнее — проверять в рантайме
import/export в глобальном .d.ts Без импортов, либо обернуть в declare global { … }
Дополнять библиотечный тип повторным type interface + module augmentation
declare module в не-модуле или с неверным именем Файл-модуль (export {}) + имя буква в букву
@types любой версии Согласовать версии; встроенные типы — @types убрать
namespace для структуры приложения Модули (файл = модуль), точечные export
Мешать import = require с ES import ES-синтаксис; для CommonJS — esModuleInterop

Коротко

  • Забыли import type — импорт остаётся в рантайме (лишний код и побочные эффекты), а при verbatimModuleSyntax это прямая ошибка TS1484. Чисто-типовое помечайте import type или import { type X }.
  • declare — обещание без проверки, как as. Описали gtag, а скрипта нет → gtag is not defined в рантайме, компилятор молчит. Убеждайтесь, что описанное есть; внешнее — проверяйте.
  • Случайный import/export в глобальном .d.ts превращает его в модуль, и глобальные объявления «пропадают». Держите такой файл без импортов или оборачивайте в declare global { … }.
  • type не сливается (повтор = Duplicate identifier, TS2300), interface сливается. Для расширения типов — interface + augmentation.
  • Augmentation не сработал? Файл должен быть модулем (есть import/export), а имя в declare module '…' — совпадать с импортом буква в букву.
  • @types должны совпадать с версией библиотеки. Рассинхрон = типы врут. Если библиотека везёт типы сама — @types не нужен и может конфликтовать.
  • Не используйте namespace для организации кода в проекте на модулях — он мешает tree-shaking. Организуйте всё модулями.
  • Не мешайте легаси export = / import x = require(…) с ES import/export. Современный код — ES-синтаксис; для совместимости с CommonJS — опция esModuleInterop.
