Файлы объявлений (.d.ts)

Файл .d.ts — это меню в ресторане. Меню подробно рассказывает, какие есть блюда, из чего они и сколько стоят, — но само меню ничего не готовит. Кухня (реальная готовка) находится в другом месте. Точно так же .d.ts перечисляет, какие типы, функции и переменные существуют и какой у них вид, но не содержит ни одной строчки работающего кода. Ещё две картинки того же самого: это оглавление книги (список глав без самих глав) и заголовочный .h-файл из языка C (объявления отдельно, реализация отдельно). Буква d в названии — от declaration, «объявление».

Что такое .d.ts: только объявления, без реализации

Обычный файл .ts делает две вещи сразу: описывает типы и содержит работающий код (тела функций, вычисления, циклы). Файл .d.ts оставляет только первую половину — чистые объявления типов. Внутри него всё как будто невидимо помечено словом declare: «такая штука где-то существует, вот её форма — а работающий код ищи в другом месте». Такой режим называют ambient («окружающий», «фоновый»).

Разберём по строкам. interface User { … } — описание формы объекта: какие поля и каких типов. declare function getUser(id: number): User; — объявление функции: известны имя, аргументы и результат, но тела нет — только точка с запятой на месте фигурных скобок. declare const appVersion: string; — переменная, которая где-то уже создана; мы лишь сообщаем её тип.

Три источника: откуда берутся .d.ts

Файлы объявлений не появляются из воздуха. Есть ровно три пути, которыми они попадают в проект. Полезно различать их с самого начала, чтобы не путаться.

  • (а) Сгенерированы компилятором. Вы пишете обычный .ts, включаете опцию declaration: true — и tsc сам создаёт рядом .d.ts. Так библиотеки, написанные на TypeScript, раздают типы своим потребителям.
  • (б) Написаны вручную. Есть готовый JavaScript-код (свой старый или чужой), у которого нет типов. Вы вручную пишете к нему .d.ts — «карточку меню», чтобы TypeScript понимал форму этого кода.
  • (в) Идут в комплекте. Многие библиотеки уже кладут .d.ts прямо в свой пакет, так что типы приезжают вместе с установкой. Если же их нет — типы часто лежат отдельным пакетом @types/….

Ниже разберём каждый источник на примере. Начнём со второго — ручного, — потому что на нём лучше всего видно саму идею «код отдельно, типы отдельно».

Схема: один .ts превращается в .js и .d.ts

Когда библиотеку пишут на TypeScript, картина ещё нагляднее. Из одного вашего .ts компилятор порождает два файла-«потомка»: рабочий .js (его будет выполнять браузер или Node) и .d.ts (его будут читать чужие проекты, чтобы понимать ваши типы). Для этого достаточно включить опцию declaration: true.

Модульный или глобальный .d.ts

А теперь тонкость, на которой спотыкается почти каждый. Поведение .d.ts зависит от одной-единственной вещи: есть ли в нём хоть один верхнеуровневый import или export.

  • Есть import/export наверху → это МОДУЛЬ. Типы из такого файла видны только тем, кто их явно импортирует. Это как отдельная кладовая: чтобы взять — надо зайти и вынести.
  • Нет ни import, ни export → это ГЛОБАЛЬНЫЙ (ambient) файл. Все объявления из него автоматически видны везде в проекте, без всякого импорта. Это как объявление по громкой связи — слышно во всех комнатах сразу.

Где .d.ts подключают: package.json и tsconfig

Осталось понять, как эти файлы «включаются». Здесь два разных места в зависимости от роли.

Если вы ПОДКЛЮЧАЕТЕ библиотеку

У библиотеки в её package.json есть поле types (устаревший синоним — typings). Оно указывает на главный входной .d.ts пакета — ту самую «обложку меню», с которой TypeScript начинает читать типы библиотеки:

Поле main говорит «вот рабочий код» (.js), а types — «вот его типы» (.d.ts). Вам как потребителю ничего настраивать не нужно: просто import из пакета, а TypeScript по types сам найдёт объявления.

После сборки в папке dist рядом с каждым .js появится одноимённый .d.ts. Останется указать на входной из них в поле types вашего package.json — и ваша библиотека будет отдавать типы всем, кто её установит.

Коротко о ролях. declaration: true в tsconfig — «сгенерируй мне .d.ts». Поле types в package.json — «вот где лежит входной .d.ts, ищите типы здесь». Первое про создание, второе про подключение.

Коротко

  • Файл .d.ts — это «меню», а не «кухня»: в нём только объявления типов, функций и переменных, без единой строки работающего кода. Всё внутри неявно declare (ambient).
  • Реализацию писать нельзя: тело функции в .d.ts даёт ошибку TS1183 «An implementation cannot be declared in ambient contexts». Только заголовок и точка с запятой.
  • Три источника .d.ts: (а) сгенерированы tsc при declaration: true; (б) написаны вручную к существующему JS; (в) идут в комплекте с библиотекой (или отдельным пакетом @types).
  • Пара «код + типы»: math.js выполняется, одноимённый math.d.ts описывает его типы; TypeScript находит их сам, и потребитель получает автодополнение и проверки поверх нетипизированного JS.
  • Один .ts → два файла: .js (рабочий код для рантайма, «блюдо») и .d.ts (типы для тех, кто подключает, «карточка в меню»).
  • Модульный vs глобальный: есть верхнеуровневый import/export — файл модуль (типы только через импорт); нет — глобальный ambient (типы видны везде без импорта).
  • Где включают: поле types в package.json указывает на входной .d.ts библиотеки; опция declaration: true в tsconfig включает генерацию.

Дальше по теме: ключевое слово declare (тот самый механизм, что стоит за каждым объявлением в .d.ts), готовые типы библиотек @types, приём слияния объявлений (например, чтобы дополнить Window), устаревшие пространства имён и, конечно, нюансы и подводные камни — там разобрана ловушка «модуль против глобали» и другие грабли.
