TypeScript/Дженерики/В классах и интерфейсах

В классах и интерфейсах

Дженерик-класс — это чертёж-фабрика коробок. Сам по себе чертёж не знает, что будут хранить коробки: тип содержимого он оставляет как «пустое место» T. А когда вы делаете конкретную коробку — new Box<number>() — вы размечаете её под числа, и с этого момента компилятор следит, чтобы туда попадали только числа. Ровно так же ведут себя дженерик-интерфейсы и псевдонимы типов: одна форма — сколько угодно наполнений.

Дженерик-класс class Box<T>

Параметр типа объявляют в угловых скобках сразу после имени класса: class Box<T>. Дальше T можно использовать внутри класса как обычный тип — в полях, в параметрах методов, в типах возвращаемых значений. Пока класс только описан, T — это заглушка: конкретный тип встанет на его место в момент создания объекта.

Аналогия. Представьте станок, который штампует коробки. На чертеже написано «сюда кладётся что-то одного сорта» — но какого именно, чертёж не уточняет. Один и тот же станок делает и коробки под болты, и коробки под печенье. T — это и есть «сорт содержимого», который выбирают при запуске станка.

Обратите внимание: и геттер value возвращает T, и сеттер принимает T. Как только мы создали Box<number>, все T внутри превращаются в number — компилятор не даст положить туда строку. Это и есть польза дженерика: тип содержимого не теряется (сравните с any, который стёр бы его).

Создание объекта: явно или по выводу

Указать тип коробки можно двумя путями. Либо написать его явно в угловых скобках при вызове конструктора — new Box<string>('привет'). Либо ничего не писать и позволить компилятору вывести тип из аргумента конструктора — new Box(5) даст Box<number>, потому что 5 — число. Это тот же механизм вывода, что и у дженерик-функций.

Важный вывод: Box<number> и Box<string> — это разные типы, и один нельзя присвоить другому. Класс становится «номинально» различимым по своему параметру: две коробки одинакового устройства, но с разной разметкой содержимого несовместимы. Это защищает от случайного перемешивания «коробки под числа» и «коробки под строки».

Дженерик-интерфейс interface Container<T>

Интерфейсы описывают форму объекта, и они тоже умеют быть дженериками. Параметр типа ставится после имени: interface Container<T>. Внутри T используется в типах полей и методов. Это позволяет одним интерфейсом описать «контейнер для чего угодно», не плодя StringContainer, NumberContainer и так далее.

Как и с классом, при использовании интерфейса тип подставляется в угловых скобках: Container<number>, Container<string[]>. Дженерик-интерфейсы — прямое развитие обычных интерфейсов: та же идея «описать форму», только форма теперь настраиваемая.

Дженерик-псевдоним type Pair<T, U>

Параметры типа принимает и псевдоним type. Более того, параметров может быть несколько — просто перечислите их через запятую: type Pair<T, U>. Классический пример — пара из двух значений возможно разных типов.

Здесь T и U независимы: Pair<string, number> — это «строка плюс число», а Pair<number, number> — «число плюс число». Компилятор подставляет каждый параметр на своё место и следит за соответствием.

Практика: реальные дженерик-типы

Соберём несколько типовых структур, которые встречаются в реальном коде. Начнём со стека — «стопки тарелок»: класть и снимать элементы можно только сверху. Тип элементов задаётся параметром T, поэтому один класс Stack<T> годится и для чисел, и для строк, и для задач.

Заметьте T | undefined у pop и peek: стек может оказаться пустым, и честный тип это показывает — вызывающему придётся проверить результат. Это та же логика «может ничего не быть», что и у объединений с undefined.

Result<T, E = Error> — успех или ошибка

Очень удобный тип для функций, которые могут завершиться неудачей: вместо исключения они возвращают «конверт» — либо успех со значением T, либо ошибку E. У параметра E есть значение по умолчанию Error, поэтому чаще всего пишут просто Result<number>.

Repository<T extends { id: number }> — картотека

Хранилище-«картотека»: складывает записи и находит их по id. Но чтобы искать по id, надо быть уверенным, что поле id у записей вообще есть. Здесь помогает ограничение T extends { id: number }: оно требует, чтобы у любого T было числовое поле id.

KeyValueStore<K, V> — обёртка над Map

Два параметра типа: K — тип ключа, V — тип значения. Внутри — встроенный Map<K, V> (тоже дженерик!), а класс лишь даёт ему удобное имя и методы. Ограничение K extends string | number сужает ключи до разумных типов.

Аналогия. Repository<Task> — это склад под один сорт товара: на воротах висит табличка «только задачи», и кладовщик не примет коробку без инвентарного номера (id). А KeyValueStore<string, number> — шкафчики камеры хранения: у каждого номерок-ключ (строка) и содержимое (число).

Статические члены не видят T

Есть одно важное ограничение. Параметр типа T «принадлежит» экземпляру: у каждого объекта Box он свой (Box<number>, Box<string>…). А статический член — общий на весь класс, он один на всех. Связать «одно на всех» с «у каждого своё» невозможно, поэтому компилятор запрещает использовать T в статических полях и свойствах.

Аналогия. T — это ярлык на конкретной коробке («тут числа», «тут строки»). А статический член — вывеска на воротах всего завода: она одна, и не может одновременно гласить «числа» для одной коробки и «строки» для другой. Отсюда и запрет.

Обход простой: если статическому методу нужен «какой-то тип», дайте ему самому отдельный параметр типа (static of<U>(...)). Такой U не связан с T класса и потому разрешён.

Класс реализует дженерик-интерфейс

Дженерик-интерфейс отлично работает как контракт: он говорит «что» умеет структура, не навязывая «как». Класс берёт на себя выполнение контракта через implements. Улучшим наш стек: вынесем список умений в интерфейс Stack<T>, а конкретную реализацию назовём ArrayStack<T>.

Параметр T класса передаётся в T интерфейса: class ArrayStack<T> implements Stack<T>. Компилятор проверит, что класс реализовал все методы контракта с правильными типами — забыли peek или перепутали тип, и будет ошибка. Плюс контракта в том, что реализаций может быть несколько (например, стек поверх связного списка), а код, работающий с типом Stack<T>, не заметит разницы.

Метод со своим параметром типа

Отдельный параметр типа может быть не только у класса, но и у конкретного метода. Классический пример — map: он берёт Box<T> и превращает его в Box<U>, применив функцию преобразования. Тип U компилятор выведет из того, что вернёт эта функция.

Так дженерик-класс и дженерик-метод складываются вместе: numBox.map(n => `#${n}`) превращает Box<number> в Box<string>, а следующий map — обратно в Box<number>, и на каждом шаге тип содержимого известен точно.

Коротко

  • Дженерик-класс class Box<T> — чертёж-фабрика: T — «сорт содержимого», подставляется при создании объекта.
  • Тип объекта задают явно (new Box<string>('a')) или получают выводом из аргумента конструктора (new Box(5) → Box<number>). Box<number> и Box<string> — разные, несовместимые типы.
  • Дженериками бывают и интерфейсы (interface Container<T>), и псевдонимы (type Pair<T, U>) — параметров может быть несколько.
  • Типовые структуры: Stack<T>, Result<T, E = Error>, Repository<T extends { id: number }>, KeyValueStore<K, V> — один класс на любой тип содержимого.
  • Статические члены не видят T класса (он у каждого экземпляра свой). Нужен тип статике — дайте параметр самому методу: static of<U>(...).
  • Класс выполняет контракт дженерик-интерфейса через implements Stack<T>; у отдельного метода может быть свой параметр типа (map<U>).
