Значения по умолчанию

У обычного аргумента функции бывает значение по умолчанию: greet(name = "друг") — не передали имя, подставится «друг». У параметров типа есть ровно то же самое, только для типов: Container<T = string> — не передали тип, подставится string. Это как настройки прибора по умолчанию: работает из коробки под типовой сценарий, но при желании всё можно перенастроить.

Зачем дефолт у параметра типа

Дженерик-тип — это «заготовка с дыркой»: Container<T> ничего не значит, пока не подставишь конкретный T. Обычно это удобно: тип подстраивается под задачу. Но у многих заготовок есть самый частый сценарий. Контейнер чаще всего хранит строку; «ответ сервера» по умолчанию содержит данные неизвестной формы; тип ошибки в большинстве случаев — Error.

Если для типового сценария каждый раз писать аргумент типа руками (Container<string>, Result<number, Error>), код засоряется повторами. Значение по умолчанию решает это: задаём «тип из коробки» один раз в объявлении, и тогда обычный вызов Container уже работает — а редкие случаи по-прежнему можно переопределить.

Аналогия. Новый роутер работает сразу после включения: у него уже прописаны настройки по умолчанию (канал, режим, имя сети). Большинству этого хватает. Но кто хочет — заходит в панель и меняет их под себя. Дефолт у параметра типа — те самые «заводские настройки»: удобное поведение из коробки плюс возможность перенастроить.

Синтаксис <T = string>

Значение по умолчанию записывают прямо в объявлении параметра — через знак = после имени: <T = string>. Читается это буквально так же, как name = "друг" у аргумента функции: «если T не передали — считай, что это string».

Обратите внимание на строку с ошибкой: раз Container без аргумента означает { value: string }, положить туда число нельзя. Дефолт — это реальный тип, а не «что угодно»; он так же строго проверяется компилятором.

Дефолт вместе с ограничением <T extends X = Y>

Дженерики часто ограничивают — требуют, чтобы T имел определённую форму: <T extends { id: number }>. Дефолт и ограничение прекрасно уживаются вместе. Порядок такой: сначала ограничение extends X, потом значение по умолчанию = Y.

Здесь Repository<T extends Entity = Entity> читается так: «T обязан иметь поле id: number (ограничение), а если тип вообще не назвали — бери Entity (дефолт)». И то и другое работает одновременно.

Правило: дефолт обязан удовлетворять ограничению

Есть одно жёсткое требование, которое легко упустить. Значение по умолчанию Y само должно проходить проверку ограничения X. Логично: раз любое подставленное T обязано входить в X, то и тип «по умолчанию» — не исключение.

В строке <T extends string = number> ограничение говорит «только строки», а дефолт предлагает number — это противоречие, и компилятор его не пропускает. Достаточно взять дефолт, входящий в ограничение (например, литерал 'idle'), и всё встанет на место.

Порядок параметров: обязательные раньше, с дефолтом позже

Ещё одно правило один в один как у аргументов функции. Нельзя написать function f(a = 1, b) — обязательный b не может стоять после аргумента со значением по умолчанию. Точно так же и с параметрами типа: сперва идут обязательные, а параметры с дефолтом — только после них.

Практика: типовые дефолты

Соберём приёмы, которые встречаются в реальном коде постоянно. Первый — «ответ сервера». Пока форма данных не уточнена, разумно ставить дефолтом unknown: он безопасен, потому что заставляет проверить данные, прежде чем ими пользоваться (в отличие от any — про разницу см. any и unknown).

Второй классический кейс — результат операции: либо успех со значением, либо ошибка. Тип ошибки почти всегда Error, поэтому его ставят дефолтом; а когда ошибки — это, например, строковые коды, второй параметр переопределяют.

Здесь дефолт экономит писанину: в 90% случаев мы пишем просто Result<number>, и E автоматически становится Error. Это тот же приём «размеченного объединения», что и на странице Объединения — только с настраиваемым типом ошибки.

Дефолт против вывода: кто побеждает

Важно понимать, когда именно включается значение по умолчанию. Правило простое: дефолт применяется, только если тип не указан явно и его неоткуда вывести. Как только у компилятора есть способ узнать T — из явного аргумента типа или из обычного аргумента функции — дефолт молча уступает.

Явный аргумент типа отменяет дефолт

Как только вы написали Container<number>, тип по умолчанию string вообще не рассматривается — ровно как greet("Анна") не заглядывает в дефолт "друг".

Вывод из аргумента тоже сильнее дефолта

Отдельный тонкий момент для дженерик-функций: если T можно вывести из переданного аргумента, компилятор возьмёт выведенный тип, а не дефолт. Дефолт остаётся «в резерве» — на случай, когда выводить не из чего.

Отсюда практичный вывод: у функций дефолт полезен там, где T появляется только в возвращаемом типе (как makeList) и его физически неоткуда вывести. Если же T приходит через аргумент — дефолт почти никогда не сработает, потому что вывод его опережает.

Осторожно: дефолт T = any

И последнее — самая частая ловушка. Соблазнительно поставить дефолтом any, чтобы «не ругался». Но any отключает проверки, и такой дефолт незаметно проделывает дыру в типах: код компилируется, а ошибки прячутся до рантайма.

Мораль: если нужен «широкий» дефолт для неизвестных данных — берите unknown, а не any. unknown так же «принимает что угодно», но заставляет проверить значение перед использованием. Эта и другие тонкости разобраны на странице Нюансы и подводные камни.

Коротко

  • Значение по умолчанию у параметра типа — это «тип из коробки»: <T = string> работает как name = "друг" у аргумента функции. Не передали тип — подставится дефолт.
  • Дефолт — реальный тип и проверяется строго: Container без аргумента означает { value: string }, и число туда уже не положить.
  • С ограничением дефолт совмещается (<T extends X = Y>), но дефолт обязан удовлетворять ограничению: <T extends string = number> — ошибка.
  • Порядок: обязательные параметры раньше, с дефолтом — позже. <T = string, U> запрещено («Required type parameters may not follow optional type parameters»).
  • Дефолт применяется, только когда тип не указан и его неоткуда вывести. Явный аргумент типа и вывод из аргумента функции его отменяют.
  • Не делайте дефолтом any — он маскирует ошибки. Безопасный «широкий» дефолт — unknown.
