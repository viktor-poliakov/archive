Размеченные объединения

Размеченное (его ещё называют тегированным) объединение — это главный практический паттерн работы с union из объектов. Идея на удивление простая: у всех вариантов есть общее поле-метка, а его значение — строковый литерал. По этой метке TypeScript однозначно понимает, какой именно вариант перед ним, и открывает доступ ровно к «своим» полям этого варианта. Это прямое продолжение модели «тип — это множество значений» со страницы Подтипы и супертипы.

Идея: общий ярлык у всех вариантов

Обычный union из объектов неудобен: TypeScript видит несколько форм сразу и не знает, к какой именно обратиться. Размеченное объединение решает это так — в каждый вариант добавляют одно и то же поле-метку (его называют дискриминантом), а типом этого поля делают строковый литерал, уникальный для варианта. Обычно метку называют kind, type или status.

Аналогия: посылка с ярлыком. Представьте гору посылок. Пока они закрыты, вы не знаете, что внутри. Но на каждой в углу наклеен ярлык: «хрупкое», «книги», «одежда». Достаточно взглянуть на ярлык — и сразу понятно, как обращаться с содержимым, не вскрывая коробку. Поле kind — это и есть такой ярлык: по нему TypeScript «читает», какой вариант перед ним, и что там за поля.

Самое ценное: проверив одно поле-метку, вы сужаете весь объект целиком. TypeScript автоматически понимает, что если kind === 'circle', то перед нами именно Circle со всеми его полями:

Это и есть сужение типов, только удобнее обычного: не нужно проверять наличие каждого поля по отдельности — достаточно сравнить метку. TypeScript «умеет» такое сужение именно потому, что типы меток — непересекающиеся литералы.

Как это выглядит: набор помеченных вариантов

Union из объектов удобно представлять как набор посылок, у каждой из которых свой ярлык kind. Ярлык у всех в одном и том же месте (это общее поле), но значение — своё. Остальные поля у вариантов различаются.

Исчерпывающая проверка через never

У паттерна есть суперспособность: заставить компилятор следить, чтобы вы обработали все варианты. Приём такой — в ветку default кладём присваивание значения переменной типа never:

Почему в default тип сужается до never? Вспомним, что never — это пустое множество, «низ» иерархии (см. void и never). Каждая ветка case «отрезает» от объединения свой вариант. Когда обработаны 'circle', 'rectangle' и 'triangle', вычитать из объединения больше нечего — не остаётся ни одного возможного значения. А тип, в котором нет значений, — это ровно never. Значит, если все ветки на месте, shape в default имеет тип never, и присваивание const _exhaustive: never = shape проходит.

А теперь — ради чего всё затевалось. Допустим, спустя полгода в объединение добавили новую фигуру, а ветку в switch дописать забыли. Тогда до default будет «доходить» этот новый вариант, тип перестанет быть never, и присваивание перестанет компилироваться:

Ошибка вместо тихого бага. Без проверки через never забытая фигура молча вернула бы undefined где-то в рантайме. С ней компилятор укажет точное место ещё до запуска. Такую переменную часто выносят в отдельную функцию assertNever(x: never) и вызывают в каждом default.

Почему это лучше «объекта-бога»

Новички часто описывают состояние иначе — одним «толстым» типом, где все возможные поля свалены вместе и сделаны опциональными. Назовём это «объектом-богом»:

Проблема в том, что тип не связывает поля со статусом. Он разрешает и «пустой успех» без data, и абсурдные комбинации вроде «загрузка с данными и ошибкой одновременно». Компилятор молчит, а баги всплывают в рантайме. Размеченное объединение делает невозможные состояния невыразимыми:

Что проверяем Объект-бог (опциональные поля) Размеченное объединение
Невозможные состояния ❌ можно собрать (загрузка + данные) ✅ отсекаются компилятором
Доступ к полям ❌ всё опционально, всюду нужен ?. ✅ поле доступно только в своей ветке
Забыли новый вариант ❌ тишина, узнаете в рантайме ✅ ловит проверка через never

В терминах множеств разница наглядна. «Объект-бог» — это одно широкое множество, куда попадают и осмысленные, и бессмысленные объекты. Размеченное объединение — это объединение узких, непересекающихся множеств: каждое состояние строго очерчено, лишнему туда не попасть.

Дискриминант обязан быть литеральным типом

Весь фокус держится на одном условии: тип поля-метки — строковый литерал ('circle'), а не широкий string. Только по непересекающимся литералам TypeScript умеет однозначно разводить варианты. Если метка вдруг вывелась как string, сужение ломается:

Ловушка тут в выводе типов: у обычного const-объекта поле-строка выводится как широкий string, а не как литерал. Лечится это либо явной аннотацией типа переменной, либо добавлением as const, которое «замораживает» строки до литералов. Подробнее — на страницах Литеральные типы и Приведение (as).

Практический вывод: дискриминант почти всегда пишут строковым литералом (kind: 'circle') прямо в определении типа. Внутри такого типа поле уже литеральное — проблема из примера выше возникает лишь тогда, когда объект собирают «вручную» без аннотации.

Коротко

  • Размеченное объединение — union объектов с общим полем-меткой (дискриминантом), тип которого — строковый литерал.
  • Проверка одной метки (kind, status…) сужает весь объект до нужного варианта — в ветке доступны только «свои» поля.
  • Основной инструмент — switch по дискриминанту; обращение к чужому полю — ошибка компиляции.
  • Исчерпывающая проверка: const _exhaustive: never = x в default. Пропустили вариант — тип перестаёт быть never, и код не соберётся.
  • Паттерн лучше «объекта-бога» с опциональными полями: невозможные состояния становятся невыразимыми.
  • Дискриминант обязан быть литералом, а не широким string; при ручной сборке объекта помогает as const.
