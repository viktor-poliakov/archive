Нюансы и подводные камни

Объединения и сужение выглядят просто, пока не столкнёшься с мелочами: то typeof ведёт себя не так, как ждёшь, то сужение внезапно «отваливается», то filter оставляет в типе лишнее. Здесь собраны самые частые грабли — с объяснением, почему так, и как сделать правильно. Если базовые механизмы ещё в новинку, начните с Сужения типов.

1. typeof null === 'object'

Историческая ошибка самого JavaScript: у null оператор typeof возвращает 'object'. Поэтому проверка typeof x === 'object' пропускает внутрь не только объекты и массивы, но и null — и сужение получается не таким, как вы рассчитывали.

Отсекать null надёжнее прямым сравнением x !== null (или проверкой на истинность, если пустые значения вам не важны).

2. Проверка на истинность съедает 0 и ''

Условие if (x) удобно, чтобы отсечь null и undefined. Но falsy-значений больше: 0, пустая строка '' и NaN тоже «провалят» проверку — хотя это совершенно нормальные значения.

Правило. Проверку if (x) применяйте, когда «пусто» и «ноль» для вас — одно и то же. Если 0 или '' осмысленны, сужайте явно: x !== undefined, x != null.

3. Сужение теряется в колбэках и при переприсваивании

Анализ потока управления работает линейно и по месту. Сужение надёжно держится, пока код идёт сверху вниз — даже через вызовы функций. Но оно сбрасывается в двух ситуациях: когда обращение к значению уезжает внутрь колбэка (он выполнится когда-то потом, и к тому моменту значение могло измениться) и когда переменную где-то переприсваивают.

Вторая ситуация — переменную захватывает замыкание, а ниже ей присваивают другое значение:

Частый миф. Говорят, будто сужение «слетает после любого вызова функции или await». Это не так: в линейном коде TypeScript сохраняет сужение и после вызова, и после await. Теряется оно именно в отложенном коде (колбэки, обработчики событий) и при переприсваивании переменной. Лекарство — работать с const или скопировать суженное значение в отдельную переменную.

4. .filter(Boolean) не сужает тип

Классический приём «выкинуть пустые элементы» через arr.filter(Boolean) в рантайме работает, но тип массива не меняет: компилятор не знает, что предикат отсёк именно null/undefined. В типе они остаются — и вы получаете ошибку «possibly undefined» на следующем шаге.

Решение — предикат-guard прямо в стрелке: (s): s is string => …. Он сообщает filter, какой тип остаётся на выходе. Подробнее — на странице Проверки типов.

5. Дискриминант обязан быть литералом

Сужение размеченного объединения держится на том, что поле-метка имеет литеральный тип ('circle'), а не широкий string. Но при выводе типа обычного объекта TypeScript расширяет строковый литерал до string — и объект внезапно перестаёт подходить под union.

Помогает as const (фиксирует литеральные типы) или явная аннотация целевым типом. Тема литералов и их расширения — на странице Литеральные типы.

6. Оператор in: ключ есть — значение может быть undefined

Оператор in отвечает на вопрос «есть ли у объекта такой ключ», а не «задано ли значение». Для опционального свойства { cache?: boolean } его тип — boolean | undefined, и проверка 'cache' in config этот undefined не убирает.

Оператор in хорош, чтобы различать разные по форме члены union (у одного есть поле, у другого нет). А вот «есть ли значение» надёжнее спрашивать напрямую у значения.

7. Union функций почти невозможно вызвать

Если переменная имеет тип «одна функция или другая», TypeScript, вычисляя тип параметра для вызова, пересекает типы параметров вариантов. Для (x: string) => void и (x: number) => void это даёт string & number — то есть never. Позвать такую функцию нечем.

Это не баг, а следствие безопасности: аргумент должен подойти любому из вариантов. Выход — сначала сузить union до одной конкретной функции, а уже потом вызывать.

8. switch без break — проваливание

Наследие JavaScript: если ветка case не заканчивается break или return, выполнение «протекает» в следующий case. Это источник неочевидных багов — но здесь TypeScript на вашей стороне: строгая опция noFallthroughCasesInSwitch (входит в набор проекта) ловит проваливание ещё при компиляции.

Самая надёжная привычка — возвращать значение прямо из case (return): тогда проваливание невозможно в принципе, а заодно каждая ветка обязана дать результат.

9. as — это «затычка», а не проверка

Когда сужение не выходит, велик соблазн «объяснить» компилятору тип через приведение as. Но as ничего не проверяет во время работы программы — он лишь затыкает рот компилятору. Если реальные данные окажутся другими, ошибка просто переедет из этапа компиляции в рантайм, где её ловить куда неприятнее.

Приведение as уместно, когда вы знаете о типе больше компилятора и берёте ответственность на себя. Но для внешних данных честнее проверить форму guard'ом. Подробнее о рисках as — на странице Приведение (as).

Коротко

  • typeof null === 'object' — typeof не отсекает null; убирайте его сравнением !== null.
  • Проверка if (x) заодно отбрасывает 0, '', NaN — при осмысленных «нулевых» значениях сужайте явно.
  • Сужение держится в линейном коде (даже после вызовов и await), но теряется в колбэках/замыканиях и при переприсваивании. Спасают const и копия значения в отдельную переменную.
  • .filter(Boolean) не меняет тип — для сужения массива нужен предикат-guard (x): x is T.
  • Дискриминант размеченного объединения должен быть литералом (следите за расширением до string; помогает as const).
  • in проверяет наличие ключа, а не заданность значения; union функций сводит параметр к never.
  • as не проверяет данные, а отключает контроль — для внешних данных предпочитайте guard.
