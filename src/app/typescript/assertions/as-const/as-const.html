TypeScript/Приведение и утверждения/as const

as const

as const — это команда компилятору: «заморозь это значение как есть». Заморозь в двух смыслах сразу: возьми самый узкий из возможных типов (не «какая-то строка», а ровно вот эта строка) и сделай всё содержимое только для чтения (readonly). Аналогия — консервация: обычная переменная как свежий продукт, «мягкая», её тип легко «расплывается» и расширяется; а as const — как закатать банку: значение застыло в одном состоянии, и его форму уже не поменять.

Проблема: литералы «расплываются»

Чтобы понять, зачем нужен as const, сначала посмотрим на боль. Литерал — это конкретное значение, вписанное прямо в код: строка 'idle', число 42, true. Казалось бы, если мы написали 'idle', то и тип должен быть 'idle'. Но TypeScript часто выводит более широкий тип — string. Это явление называют расширением литерала (literal widening).

Логика тут простая и разумная. Раз в let-переменную завтра можно записать любую другую строку, нет смысла держать узкий тип 'idle' — компилятор заранее расширяет его до string. А const-переменную переприсвоить нельзя, значит её значение застыло, и тип можно оставить узким — 'idle'.

Но с объектами const не помогает вглубь

Кажется, что решение найдено: пиши const — и литералы сохранятся. Для одиночных примитивов так и есть. Но как только значение — объект или массив, const перестаёт помогать внутри. И вот почему.

const защищает только саму ссылку на объект — переменную o нельзя переприсвоить на другой объект. Но поля внутри объекта остаются свободно изменяемыми: o.status = 'loading' компилятор разрешит. А раз поле status в будущем может стать любой строкой, TypeScript честно и выводит его тип как string, а не как узкий 'idle'. То же с массивами: [1, 2, 3] становится number[], потому что в массив можно и дописать, и переписать элементы.

as const «замораживает» значение

Именно эту проблему и решает as const. Приписав его к значению, вы говорите компилятору: перестань расширять и разрешать изменения — возьми самый узкий тип и пометь всё как readonly. Три следствия, по одному на каждый вид значения:

  • Строки, числа, boolean → превращаются в литеральные типы: 'idle' вместо string, 42 вместо number.
  • Объекты → все поля становятся readonly и получают литеральные типы.
  • Массивы → превращаются в readonly-кортежи (tuple): фиксированная длина, порядок и типы элементов.

Обратите внимание на let в первых двух строках — это не опечатка. Для одиночных примитивов as const заметен только с let: у const литерал сохраняется и без него (const a = 'idle' уже даёт тип 'idle', мы разобрали это выше), а let без утверждения расширился бы до string. С объектами и массивами всё наоборот: там const не спасает, и as const нужен именно в паре с ним — поэтому ниже в примере снова const.

Значение Тип без as const Тип с as const
'idle' (в let) string 'idle'
42 (в let) number 42
{ status: 'idle' } { status: string } { readonly status: 'idle' }
[1, 2, 3] number[] readonly [1, 2, 3]

Аналогия. Свежий продукт — «мягкий»: он меняется, портится, форму держит плохо (это расширение типа). Закатать в банку — значит зафиксировать содержимое в одном состоянии: ничего не добавить, не убрать, не подменить. as const и есть та самая «закатка» для значения на уровне типов.

Практика A: неизменяемый конфиг

Самое частое применение — константы и конфиги, которые не должны меняться после объявления. Обычный объект легко испортить случайным присваиванием где-нибудь в глубине кода. as const закрывает эту дверь: любая попытка записи в поле становится ошибкой ещё на компиляции.

Обратите внимание: читать поля можно как обычно (CONFIG.apiUrl), а вот перезаписать — уже нет. Компилятор превратил конфиг в «только для чтения» и заодно запомнил точные значения полей как литеральные типы.

Практика B: union-тип из массива

Это один из самых полезных приёмов с as const, который встречается постоянно. Идея: держать список допустимых значений в одном массиве, а тип-объединение из него вывести автоматически, чтобы не дублировать один и тот же список руками в двух местах.

Разберём загадочную строку type Role = typeof ROLES[number] медленно, по кусочкам — здесь два новых для новичка приёма.

  • typeof ROLES — это typeof на уровне типов (не тот typeof, что работает в рантайме!). Он берёт тип переменной ROLES — а благодаря as const это readonly ['admin', 'editor', 'guest'].
  • [number] — это индексный доступ. У кортежа мы «спрашиваем» тип элемента по индексу. Если индекс — конкретное число ([0]), получим тип одного элемента. А если индекс — тип number (то есть «любой числовой индекс»), получим тип любого элемента, то есть объединение всех: 'admin' | 'editor' | 'guest'.

Почему без as const не работает. Без него тип массива был бы string[]. Тогда typeof ROLES[number] дал бы просто string — не список конкретных ролей, а «любая строка». Весь смысл приёма именно в том, что as const сохранил литералы 'admin' | 'editor' | 'guest'.

Практика C: точный кортеж вместо массива

Иногда массив на самом деле — не «список из чего-то одного», а пара (или тройка) значений фиксированной формы: координаты [x, y], размеры [ширина, высота], пара «значение и функция». Обычный вывод превращает такое в размытый number[] и теряет и длину, и порядок. as const закрепляет форму — получается кортеж (tuple).

Особенно ярко это видно на паре «значение + функция» — так устроен, например, useState в React. Без as const оба элемента слились бы в один общий тип-мешанину, и при разборе const [isOpen, toggle] = ... было бы непонятно, где boolean, а где функция. С as const компилятор точно знает: первый элемент — boolean, второй — функция, и типы разъезжаются по своим местам.

Практика D: действия и размеченные объединения

Ещё один частый случай — объекты-действия (actions), которые описывают «что произошло»: { type: 'increment', by: 1 }. Такие объекты обычно складывают в размеченное объединение (discriminated union), где поле-тег type позволяет компилятору сузить объект до нужной ветки. Но сужение сработает, только если тег — литерал 'increment', а не размытый string.

Здесь as const играет решающую роль: без него поле type расширилось бы до string, и объект перестал бы подходить под тип Action (ведь string — это не только 'increment' или 'reset'). С as const тег зафиксирован как литерал — и всё сходится.

Два важных нюанса

1. readonly — глубокий

Заморозка от as const действует на любую глубину (её называют deep readonly). Одно as const в конце выражения делает readonly не только верхние поля, но и все вложенные объекты и массивы. Не нужно расставлять as const на каждом уровне.

2. Это подсказка типам, а не действие в рантайме

Как и другие утверждения (as, оператор !), as const живёт только на этапе типов. Он ничего не делает во время выполнения программы: не копирует значение и не замораживает его по-настоящему. В скомпилированном JavaScript от него не остаётся и следа.

Важно не путать. as const — это обещание компилятору «я не буду это менять», и компилятор помогает его сдержать, подсвечивая ошибки. Но если данные «обойти» приведением as, в рантайме они изменятся: настоящей защиты значения нет. Реальную заморозку во время выполнения даёт Object.freeze(), а as const — только типы.

Коротко

  • as const = «заморозь как есть»: самый узкий (литеральный) тип + всё readonly. Аналогия — консервация: значение застывает в одном состоянии.
  • Проблема, которую он лечит — расширение литералов: let s = 'idle' даёт string, а объектам не помогает даже const, потому что их поля мутабельны.
  • Что делает по видам значений: строки/числа → литеральные типы; объекты → readonly-поля с литералами; массивы → readonly-кортежи.
  • Union из массива: const ROLES = [...] as const, затем type Role = typeof ROLES[number] — один источник правды вместо дублирования списка.
  • Точный кортеж вместо number[] — для координат, пар «значение + функция» (как useState) и других структур фиксированной формы.
  • Фиксирует тег type: 'increment' как литерал — без этого размеченные объединения и сужение не работают.
  • readonly глубокий, но действует только на уровне типов: в рантайме значение не копируется и не замораживается — для этого нужен Object.freeze().

Дальше по теме: как литеральные типы устроены в основе — Литеральные типы. Соседние утверждения — приведение as и оператор non-null (!). Где as const раскрывается на практике — размеченные объединения. А типичные ошибки с утверждениями собраны в разделе нюансы и подводные камни.
