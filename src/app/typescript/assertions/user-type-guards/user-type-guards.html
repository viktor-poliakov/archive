Пользовательские type guards (is)

Пользовательский type guard (страж типа) — это охранник на входе в клуб. Он проверяет документы (реально смотрит на значение) и, если всё в порядке, ставит на руку штамп «проверено — это точно VIP». Дальше по этому штампу человека пропускают везде, никто документы больше не спрашивает. В TypeScript таким «штампом» служит особый тип, который функция возвращает, — value is Type. Функция сама проверяет тип и «докладывает» результат компилятору, а тот дальше сам сужает тип по её слову.

Проблема: встроенных проверок не хватает

На странице про typeof и instanceof мы видели: этих двух операторов достаточно для простых случаев. typeof различает примитивы ('string', 'number', 'boolean'), а instanceof — экземпляры классов (Date, Error, ваши собственные классы). Пока значение — строка или объект известного класса, всё хорошо.

Но реальные данные редко бывают такими удобными. Ответ от сервера — это обычный объект вроде { id: 1, name: 'Аня' }, а не экземпляр класса, поэтому instanceof к нему неприменим. А typeof для любого объекта возвращает лишь строку 'object' — он видит, что это «что-то объектное», но не видит формы: есть ли поле id, какого оно типа. Точно так же встроенные операторы не помогут выбрать один вариант из объединения, различающегося по значению поля. Для этих задач нужен инструмент, который проверит что угодно и сам объяснит результат компилятору.

Синтаксис: возвращаемый тип v is Type

Пользовательский type guard — это самая обычная функция. Отличие ровно одно: вместо boolean в возвращаемом типе стоит особая конструкция v is Type. Её называют тип-предикатом (type predicate — «утверждение о типе»).

Разберём эту строку по косточкам, потому что здесь и кроется вся идея. Запись function isString(v: unknown): v is string состоит из частей:

  • v — имя параметра, о котором функция делает утверждение. Оно должно совпадать с именем в скобках.
  • : unknown — что функция принимает на вход. Здесь unknown («что угодно, но потребуй проверки»), но может быть и объединение, и любой другой тип.
  • : v is string — сам предикат. Он заменяет boolean и читается так: «если функция вернула true, то v — это string».
  • тело return typeof v === 'string' — настоящая проверка. Она обязана вернуть true или false.

Аналогия со штампом. Функция-предикат — это охранник. Тело return ... — момент, когда он смотрит документы. А возвращаемый тип v is string — штамп на руке: «я проверил, это точно строка». Компилятор — это остальные сотрудники клуба: сами документы они не смотрят, а верят штампу охранника и пускают дальше.

Как TS сужает тип по предикату

Ради чего всё затевалось: после вызова guard в условии if компилятор сужает тип автоматически. До проверки значение — широкое unknown; в ветке, где guard вернул true, тип становится узким; в ветке else этот вариант вычитается.

Практика A: проверка формы объекта

Самый частый повод завести guard — внешние данные: ответ API, разобранный JSON.parse, содержимое формы. Их форму TypeScript знать не может (для него это unknown), поэтому мы проверяем её вручную — шаг за шагом. Порядок проверок важен: сначала грубые (это вообще объект?), потом точные (нужного ли типа поля?).

Обратите внимание на шаг v !== null: без него guard был бы дырявым, ведь typeof null тоже даёт 'object' — это давняя особенность JavaScript. И заметьте (v as User).id внутри тела: здесь as уместен, потому что мы тут же проверяем это поле в рантайме через typeof. Само по себе as ничего не проверяет — но мы и не полагаемся на него, а используем лишь чтобы дотянуться до поля для настоящей проверки.

Практика B: выбор члена объединения

Второй классический случай — размеченное объединение, где у каждого варианта есть общее поле-«ярлык» (дискриминатор). Guard проверяет значение этого ярлыка и сообщает компилятору, какой именно вариант перед нами.

Здесь предикат a is Cat делает ровно то, что нужно: в ветке if компилятор уверен, что a — это Cat, а в else из объединения Cat | Dog остаётся только Dog. Вся логика выбора спрятана в одну переиспользуемую функцию.

Практика C: сужение массива через .filter

Очень частая задача — убрать из массива «пустышки» (null и undefined). Проблема в том, что filter с функцией, которая возвращает просто boolean, не меняет тип: даже отбросив все null, TypeScript по-прежнему считает элементы string | null. А вот если передать в filter guard-предикат — тип элементов сузится по-настоящему.

Почему так. Метод filter имеет специальную перегрузку: если ему передать функцию с предикатом v is T, он возвращает уже T[]. Guard isDefined сделан дженериком, чтобы работать с массивом любого типа — (string | null)[] превращается в string[], (Task | undefined)[] — в Task[], и так далее.

Про современный TypeScript. Начиная с версии 5.5 компилятор умеет сам вывести предикат для простой встроенной стрелки — например, raw.filter((s) => s !== null) он тоже сузит до string[]. Но именованный guard всё равно предпочтительнее: его видно по имени, он переиспользуется и одинаково надёжно сужает даже сложные проверки формы, где авто-вывод не срабатывает.

Опасность: предикат — это ваше обещание

Здесь спрятана главная ловушка, и её важно понять до конца. Компилятор не проверяет, что тело функции действительно соответствует предикату. Вы написали : v is string — TS просто верит этому на слово, чем бы ни было тело. Если тело проверяет не то (guard «лжёт»), компилятор окажется обманут, а ошибка тихо уедет в рантайм.

Важно. Предикат v is Type — это обещание, за которое отвечаете вы, а не гарантия от компилятора. Это роднит guard с приведением as и оператором !: все они говорят компилятору «поверь мне» и не проверяют данные сами. Разница в том, что у честного guard внутри стоит настоящая рантайм-проверка — но следить за её правильностью должны вы. Пишите тело внимательно и покрывайте guard тестами.

Чем это отличается от обычного boolean

Логичный вопрос: «Функция ведь и так возвращает true/false — зачем этот is?» Ответ: без предиката сужения не происходит. Обычная функция, возвращающая boolean, для компилятора — «чёрный ящик»: он видит, что она вернула true, но не знает, что это означает для типа аргумента. Предикат как раз и объясняет ему смысл проверки.

Критерий Обычная функция : boolean Type guard : v is Type
Проверяет значение в рантайме ✅ да ✅ да
Сужает тип в ветке if ❌ нет, тип остаётся широким ✅ да, тип становится узким
Работает с .filter для сужения массива ❌ нет, тип элементов не меняется ✅ да, (T | null)[] → T[]
Кто отвечает за правильность тела компилятор проверяет возврат boolean ❌ вы — предикат TS не сверяет

Итог: return в обеих функциях может быть посимвольно одинаковым — вся разница в возвращаемом типе. Одно слово is превращает «немой» boolean в инструмент, который управляет сужением.

Коротко

  • Type guard — обычная функция, но её возвращаемый тип — предикат v is Type. Аналогия: охранник проверяет документы и ставит штамп, которому дальше все верят.
  • Синтаксис: function isString(v: unknown): v is string { return typeof v === 'string'; }. v — параметр, v is string — предикат, тело — настоящая проверка, возвращающая boolean.
  • TS сам сужает тип по предикату: в ветке if (isX(v)) тип v становится узким, в else вариант вычитается.
  • Где нужен: проверка формы объекта (isUser), выбор члена объединения по дискриминатору (isCat), сужение массива через filter(isDefined).
  • Опасность: предикат — ваше обещание, TS не сверяет его с телом. Соврал guard — обманут весь код, ошибка уедет в рантайм. Это роднит guard с as и !.
  • Отличие от boolean: без is сужения не происходит вовсе. Один и тот же return, разный возвращаемый тип — разный результат.
  • Форму внешних данных проверяйте guard-ом, а не «обещайте» её через as: только реальная проверка защищает от кривых данных.
