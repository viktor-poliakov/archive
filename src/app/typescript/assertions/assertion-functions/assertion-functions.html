TypeScript/Приведение и утверждения/Assertion-функции

Assertion-функции

Assertion-функция (функция-утверждение) — это КПП со шлагбаумом. Она не говорит «да» или «нет», как вежливый охранник на фейс-контроле. Она делает жёстче: если с данными всё в порядке — молча пропускает дальше, и весь код за шлагбаумом уже уверен, что проверка пройдена. А если что-то не так — вообще не пропускает: бросает исключение, и выполнение обрывается. Технически это функция с особой аннотацией asserts: asserts condition или asserts v is Type.

Боль: проверять одно и то же снова и снова

Начнём с ситуации, знакомой каждому. Мы достаём элемент со страницы, и его тип — HTMLElement | null: браузер не гарантирует, что элемент существует. Компилятор поэтому требует проверку на null перед каждым обращением к элементу.

Мы точно знаем, что элемент есть, но вынуждены писать if (input) снова и снова. Хочется по-другому: проверить один раз в самом начале — и дальше обращаться к input спокойно, без null. Ровно для этого и придуманы assertion-функции. Одна проверка «на входе», после которой весь код ниже считается уже суженным.

Синтаксис 1: asserts condition

Самая универсальная форма. Функция принимает какое-то условие и обещает: «если я вернулась, а не бросила, то условие истинно». Это обещание записано в возвращаемом типе — asserts condition, где condition — это имя параметра, а не тип.

Разберём по шагам. Параметр condition имеет тип unknown — сюда можно передать любое выражение-проверку, например input !== null. Внутри тела: если условие ложно — throw, и функция никогда не «вернётся». Значит, любая строка после удачного вызова выполняется только тогда, когда условие было истинным — и компилятор имеет полное право сузить типы, опираясь на это. По сути assert(input !== null) работает как оператор !, только не в одном месте, а сразу для всего кода ниже — и, в отличие от !, честно падает в рантайме, если данные всё же плохие.

Синтаксис 2: asserts v is Type

Вторая форма утверждает не абстрактное условие, а конкретный тип конкретной переменной. Записывается как asserts v is Type — «утверждаю, что параметр v имеет тип Type». Похоже на пользовательский type guard (v is Type), но с добавленным словом asserts и другим поведением — не возврат, а бросок.

Обратите внимание на область действия. После вызова assertIsString(raw) переменная raw имеет тип string во всём остальном теле функции — до самого return. Не нужно оборачивать использование в if: assertion-функция «выпрямляет» тип на весь код, идущий следом.

Аналогия. Type guard — это фраза «покажи паспорт», после которой вы сами решаете, что делать с ответом (пустить или нет). А assertion-функция — это турникет: приложил проверку и прошёл, дальше все считают, что пропуск действителен. Не прошёл — застрял на входе, дальше пути нет.

Assertion-функция против type guard

Это ключевое различие, ради которого стоит остановиться. Обе конструкции «сужают» тип, но делают это по-разному и в разных местах. Type guard возвращает boolean и сужает тип только внутри if. Assertion-функция бросает исключение и сужает тип во всём коде после вызова. Наглядно — две «дорожки»:

Критерий Type guard (v is Type) Assertion-функция (asserts v is Type)
Что делает при провале проверки возвращает false бросает исключение
Возвращаемое значение boolean void (ничего)
Где действует сужение только внутри if весь код после вызова
Как вызывают if (isString(v)) { … } assertIsString(v);
Когда удобнее есть запасной путь (else) плохие данные = «дальше нельзя»

Выбор простой. Нужна развилка («если строка — одно, иначе — другое») — берите type guard. Нужно гарантировать условие и рухнуть, если оно нарушено («без этого дальше работать нельзя») — берите assertion-функцию.

Практика: валидация данных и инварианты

Главное применение — проверка данных из внешнего мира: ответа API, содержимого формы, localStorage. Такие данные приходят как unknown, и им нельзя верить на слово. Assertion-функция проверяет их форму в рантайме и, если всё хорошо, сужает тип для всего кода ниже.

Важно: это не то же, что as. Соблазнительно написать const user = data as User — и компилятор замолчит. Но приведение as и ! ничего не проверяют в рантайме: они лишь подсказка компилятору «поверь мне». Если сервер вернул мусор, as его пропустит, и программа упадёт где-то позже и непонятно почему. Assertion-функция же реально проверяет данные и падает сразу, в понятном месте, с внятным сообщением.

Второе применение — проверка инвариантов, то есть утверждений «этого не может быть». Классика — функция assertNever для исчерпывающего switch. Она принимает never и служит «стоп-краном»: если вы забыли обработать один из вариантов, компилятор поймает это ещё до запуска.

Важные нюансы: без аннотации не работает

Здесь ошибаются чаще всего, поэтому запомните два правила. Первое: аннотацию asserts … нельзя опустить. Именно она превращает обычную функцию в «утверждающую». Если её забыть, TypeScript увидит рядовую функцию, которая иногда бросает ошибку, и не будет сужать типы — вывод типов ниже вызова останется прежним.

Второе правило касается функций, присвоенных переменным (стрелочных, const assert = …). Для них TypeScript требует явную аннотацию типа самой переменной. Без неё вы получите характерную ошибку прямо в месте вызова: «Assertions require every name in the call target to be declared with an explicit type annotation».

Как правильно. Пишете assertion-функцию через обычное объявление function — просто не забывайте : asserts … в сигнатуре. Присваиваете стрелку в const — обязательно указывайте тип переменной целиком: const assert: (c: unknown) => asserts c = …. Проще всего избегать проблемы, объявляя такие функции через function.

Связь с Node.js

Если вы работали с Node, то, скорее всего, уже встречали похожее — встроенный модуль node:assert. Его функция assert(value, message?) бросает AssertionError, когда значение ложно, а её типы в TypeScript размечены ровно как assertion-функция. То есть она не только проверяет в рантайме, но и сужает типы в коде ниже — тот же механизм, что мы разбирали.

Так что node:assert — это готовая assertion-функция «из коробки». Понимая, как устроен asserts, вы понимаете и её поведение: почему после assert(x) компилятор вдруг перестаёт ругаться на x.

Коротко

  • Assertion-функция — это КПП: она не возвращает да/нет, а бросает исключение, если условие ложно. Вернулась молча — значит условие истинно.
  • Если функция не бросила, компилятор считает весь код ниже вызова уже суженным — не нужно оборачивать в if.
  • Две формы: asserts condition (утверждает произвольное условие) и asserts v is Type (утверждает конкретный тип переменной).
  • Отличие от type guard: guard возвращает boolean и сужает только внутри if; assertion-функция бросает и сужает весь код после вызова.
  • Это не as: assertion-функция реально проверяет данные в рантайме и падает в понятном месте, а as и ! лишь молча «обещают» тип.
  • Аннотацию asserts … нельзя опустить — без неё сужения не будет. Для const assert = … нужна явная аннотация типа переменной.
  • Применения: валидация внешних данных (ответ API, формы), проверка инвариантов (assertNever). В Node это уже готовый node:assert.

Дальше стоит сравнить механику с пользовательскими type guard и посмотреть, чем это отличается от опасного приведения as и оператора !. Общая теория сужения — на странице сужение типов, а про тип never (нужен для assertNever) — на странице void и never. Типичные ошибки собраны в разделе нюансы и подводные камни.
