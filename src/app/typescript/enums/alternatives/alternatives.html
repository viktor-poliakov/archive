Альтернативы enum

Представьте список разрешённых ответов в анкете. Иногда достаточно записать в правилах: «допустимо: да / нет / не знаю» — это просто перечень, он ничего не делает, только ограничивает выбор. Так работает объединение литералов (union) — это чистый тип, ноль кода в рантайме. А иногда нужен реальный выпадающий список, по которому можно кликать и перебирать пункты, — это уже объект, живущий в программе. Такую роль играет объект as const: он даёт и тип, и настоящие значения. Обе эти конструкции часто заменяют enum — и нередко оказываются удобнее.

Зачем вообще искать замену enum

С enum всё выглядит просто, пока не заглянешь под капот. В отличие от типов (type, interface), которые полностью исчезают при компиляции, числовой enum превращается в реальный объект в готовом JavaScript — и тащит за собой две особенности, о которых легко забыть.

Первая причуда — обратный маппинг (reverse mapping): числовой enum кладёт в объект и имена, и числа, поэтому Object.keys и перебор значений выдают вдвое больше, чем ожидаешь. Вторая, куда опаснее, — дыра в безопасности: обычное число (переменная, результат функции) присваивается числовому enum без ошибки. Компилятор ругается только на числовой литерал вне диапазона, но не на переменную типа number. Подробный разбор этих ловушек — на странице Нюансы и подводные камни.

А как же const enum? Он задуман, чтобы «схлопнуть» перечисление в чистые константы без объекта. Но под сборщиком с включённым isolatedModules (а это режим Angular-проектов, как наш) компилятор не инлайнит его, а эмитит тот же самый объект-enum. То есть в таком проекте const enum не даёт выгоды — см. const enum. Поэтому и родились более лёгкие альтернативы.

Альтернатива A: объединение строковых литералов

Самый лёгкий вариант — объединение литеральных типов. Вы просто перечисляете допустимые значения через |, как разрешённые ответы в анкете. Это чистый тип: он существует только на этапе компиляции и в готовый JavaScript не попадает ни единым символом.

Опираясь на модель «тип — это множество значений», такой union читается буквально: множество из четырёх конкретных строк. Всё, что вне набора, компилятор отклонит — а редактор подскажет варианты в автодополнении. Union отлично живёт как тип параметра и как основа для switch:

Обратите внимание: чтобы описать статусы заказа, разобрать их в switch и защититься от опечаток, нам не понадобился ни один объект в рантайме. Если всё, что нужно, — это ограничить набор значений, объединение литералов почти всегда лучший выбор.

Альтернатива B: объект as const и вывод типа по шагам

Union хорош, но у него нет «выпадающего списка»: по нему нельзя пройтись циклом и негде взять сами значения в рантайме. Если это нужно — берём обычный объект и «замораживаем» его через as const. Из одного такого объекта можно по шагам вывести ровно тот же union литералов. Разберём этот вывод как матрёшку: снимаем слой за слоем, пока не доберёмся до нужного набора значений.

Шаг 1. as const — фиксируем литералы

Без as const компилятор вывел бы для полей широкий тип string — и вся точность потерялась бы. С as const он запоминает конкретные литералы ('created', а не string) и делает поля readonly. Подробнее про сам приём — на странице as const.

Шаг 2. typeof Obj — поднимаемся к форме типа

Оператор typeof берёт из значения его тип. Для нашего объекта это структура вида «имя ключа → его литеральное значение».

Шаг 3. keyof typeof Obj — достаём ключи (имена)

Оператор keyof превращает форму типа в объединение её ключей. Важно: это имена полей ('Created', 'Paid'…), а не их значения.

Шаг 4. (typeof Obj)[keyof typeof Obj] — достаём значения

Последний слой матрёшки. Индексный доступ по всем ключам сразу возвращает объединение всех значений — тот самый union литералов, ради которого всё и затевалось.

Что это даёт сверх union

Раз объект реально существует в рантайме, по нему можно перебирать значения — и, в отличие от числового enum, массив выходит чистым, без обратного маппинга.

Ещё один удобный приём — дать объекту и одноимённому типу одно имя. TypeScript хранит типы и значения в разных пространствах имён, поэтому OrderStatus может означать сразу и объект (для доступа OrderStatus.Paid), и тип (для аннотаций). Получается почти как enum, но без его рантайм-причуд — и, в отличие от строкового enum, сюда подойдёт и голый литерал из набора.

Сравнение: enum vs union литералов vs объект as const

Соберём три инструмента в одну таблицу. Она же — быстрый ответ на вопрос «что выбрать».

Признак enum union литералов объект as const
Даёт тип? ✅ да ✅ да ✅ да (через шаги)
Есть объект в рантайме? ✅ да (числовой/строковый) ❌ нет, чистый тип ✅ да
Можно перебрать значения? ⚠️ да, но с мусором reverse mapping ❌ нет, перебирать нечего ✅ да, чистый массив
Читаемость в JSON ❌ числовой даёт цифры (2) ✅ понятные строки ✅ понятные строки
Совместимость типов номинальная (свой enum ≠ чужой) структурная (по значению) структурная (по значению)

«Номинальная» совместимость enum означает, что два разных перечисления с одинаковыми значениями несовместимы между собой, и даже голый литерал не присвоить переменной типа enum. Union и as const ведут себя «структурно»: подходит любое значение из набора, откуда бы оно ни взялось.

Что же выбрать

Правило простое и укладывается в одно дерево решений: всё зависит от того, нужен ли вам объект в рантайме.

Пара конкретных рекомендаций:

  • Нужен только тип (параметр функции, поле интерфейса, набор ролей) — берите union литералов. Ноль лишнего кода, максимальная простота.
  • Нужны ещё и значения в рантайме (перебрать список, отрисовать выпадашку, взять массив значений) — берите объект as const и выведите тип по шагам.
  • enum оправдан, если так уже принято в команде или это легаси-код, где перечисления повсюду. Тогда единообразие важнее теоретической чистоты.

Роли пользователя — типичный случай для union: значения нигде не перебираются, важен лишь допустимый набор.

А вот пример, где enum синтаксически чуть удобнее: одно объявление сразу даёт и доступ по имени Direction.Up, и готовый тип — без ручной «матрёшки» из typeof/keyof. Правда, ценой рантайм-объекта и номинальной строгости.

Наконец, union литералов прекрасно дружит с Record: он заставляет описать значение для каждого варианта из набора и не даст забыть ни одного статуса.

Коротко

  • Числовой enum тащит рантайм-объект с обратным маппингом и дырой в безопасности (любое number присваивается без ошибки), а const enum под isolatedModules не даёт выгоды. Отсюда — потребность в альтернативах.
  • Union литералов ('created' | 'paid' | …) — чистый тип: ноль кода в JS. Идеален, когда нужен только набор допустимых значений.
  • Объект as const даёт и значения в рантайме, и тип. Тип выводится по шагам: as const → typeof → keyof typeof (имена) → (typeof O)[keyof typeof O] (значения).
  • Бонус as const — Object.values возвращает чистый массив значений (у числового enum он засорён reverse mapping).
  • Выбор: только тип → union; нужен перебор/значения → as const; enum — если так принято в команде или это легаси.

Рядом полезно посмотреть: Числовые enum и Строковые enum (чтобы понять, от чего уходим), const enum и Нюансы и подводные камни. База под всем разделом — Литеральные типы и модель «тип — это множество значений».
