Строковые enum

Строковый enum — это как багажные бирки в аэропорту: код LON или NYC читается с одного взгляда, а безликий номер 1 — нет. Дело в том, что значение enum редко остаётся внутри программы: оно «утекает» в логи, в сетевые запросы, в базу данных. И там короткий строковый код оказывается куда читаемее числа. Строковый enum — это перечисление, у которого значение каждого члена — осмысленная строка, а не порядковый номер.

Синтаксис и обязательная инициализация

Объявляется строковый enum почти как числовой: ключевое слово enum, имя, а внутри — члены. Разница в одном: каждому члену через = вручную присваивается строка. Классический пример — статусы заказа в интернет-магазине:

Слева от = — имя члена (как мы обращаемся к нему в коде: OrderStatus.Paid). Справа — значение, та самая строка, которая реально окажется в переменной, в логе, в JSON. Имя и значение — разные вещи, и это важно помнить.

Значение обязан задать каждый член

Вот первое жёсткое правило строкового enum: ни один член не может остаться без значения. Если пропустить = хотя бы у одного, компилятор остановит сборку.

Почему так. У чисел есть естественное «следующее»: после 0 идёт 1, после 1 — 2. У строк такого «следующего» нет: что должно идти после "E"? Непонятно. Поэтому TypeScript не пытается угадывать строки и просто требует задать каждую явно.

Нет автоинкремента

У числового enum значения проставляются сами: пишешь enum E { A, B, C } — и получаешь A = 0, B = 1, C = 2. Это называется автоинкремент (автоматическое увеличение на единицу). У строкового enum его нет — и не может быть по причине из врезки выше.

На практике это значит: строковый enum чуть «многословнее» — каждую строку приходится выписывать руками. Но это честная цена за то, что значение получается осмысленным ("WARN" вместо 2), а не зависит от порядка членов.

В JS — односторонний объект: только имя → строка

Как и любой enum, строковый превращается в настоящий объект в скомпилированном JavaScript. Но объект этот односторонний: в нём есть связь «имя члена → строка» и нет обратной «строка → имя».

Строгий: голую строку не присвоить — и почему это хорошо

Второе важное свойство: строковый enum строгий. В переменную типа OrderStatus нельзя положить обычную строку — даже если её текст в точности совпадает со значением одного из членов. Единственный законный путь — через сам член enum.

Может показаться, что это лишняя придирчивость. На самом деле это защита, и особенно ярко она видна в сравнении с числовым enum, у которого здесь настоящая дыра в безопасности.

Что присваиваем Числовому enum Строковому enum
член самого enum (Status.Paid) ✅ можно ✅ можно
«голое» значение-литерал того же типа частично: 1 в диапазоне пройдёт ✅ безопасно: строку не примет
произвольное значение (number из переменной) ❌ ловушка: любой number пролезет без ошибки ✅ строку присвоить в принципе нельзя

То есть в числовой enum легко «случайно» затолкать невалидное значение (об этой ловушке — на странице Числовые enum и в Нюансах), а строковый такого не допускает. Если данные приходят снаружи (из формы, из сети), это заметная прибавка к надёжности.

Читаемость в логах и JSON — главный плюс

Вот ради чего строковый enum чаще всего и выбирают. Значение члена — не абстракция внутри программы: как только объект уходит в JSON.stringify, в лог или в тело HTTP-запроса, наружу «просачивается» именно оно. И тут разница между "PAID" и 1 становится решающей.

Стабильность при рефакторинге

Ещё одно тихое, но ценное преимущество. Значение строкового члена прибито к нему намертво и не зависит от того, на каком месте член стоит в списке. Можно свободно менять порядок членов, добавлять новые в начало или середину — уже сохранённые где-то строки останутся валидными.

С числовым enum этот же безобидный рефакторинг оборачивается тихой катастрофой: автонумерация «съезжает», Paid из 0 превращается в 1, и все ранее записанные в базу нули начинают означать другой статус. Подробный разбор этой и других ловушек — на странице Нюансы и подводные камни.

Числовые vs строковые: итоговая таблица

Сведём все ключевые отличия в одно место. Если коротко: числовой enum компактнее в скомпилированном виде, зато строковый — читаемее и безопаснее там, где значение покидает программу.

Свойство Числовой enum Строковый enum
Обратный маппинг (E[0] === "A") ✅ есть (объект двусторонний) ❌ нет (только имя → строка)
Автоинкремент значений ✅ есть (0, 1, 2…) ❌ нет, значение задаём каждому вручную
Читаемость в логах и JSON ❌ плохо: наружу уходит 1 ✅ отлично: наружу уходит "PAID"
Безопасность присваивания ❌ дыра: любой number пролезает ✅ строго: чужую строку не принять
Стабильность при перестановке членов ❌ значения «съезжают» ✅ значение привязано к члену
Размер объекта в JS ✅ вдвое больше ключей из-за reverse mapping компактнее: ключей ровно по числу членов

Практический вывод. Если значение enum где-либо покидает программу (сеть, база, лог, URL) — почти всегда берите строковый. Числовой оставьте для сугубо внутренних, коротко живущих значений, которым нужна компактность.

Коротко

  • Строковый enum — перечисление, где значение каждого члена — осмысленная строка (Paid = "PAID"), а не порядковый номер.
  • Значение обязан задать каждый член: пропуск = — ошибка «Enum member must have initializer». Автоинкремента нет.
  • В JS это односторонний объект: связь только «имя → строка», обратного маппинга (reverse mapping) нет — Object.keys вернёт ровно имена членов.
  • Строковый enum строгий: голую строку не присвоить, даже совпадающую по тексту. Это защита — в отличие от числового, куда «пролезает» любой number.
  • Главный плюс — читаемость в логах и JSON ("PAID" вместо 1) и стабильность значений при рефакторинге.
