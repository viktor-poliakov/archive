TypeScript/Перечисления (enum)/const enum

const enum

Представьте, что перед экзаменом вы составили шпаргалку, а потом аккуратно переписали все ответы в чистовик. Обычный enum — это отдельная методичка, которую вы всюду таскаете с собой: в готовой программе рядом с вашим кодом лежит целый объект-справочник. const enum обещает другое — взять ответы из шпаргалки и вписать их прямо в текст, а саму методичку выбросить: значения подставляются в код на этапе сборки, а объекта в рантайме не остаётся. Идея заманчивая, но, как мы увидим, именно в этом проекте она не срабатывает.

Проблема обычного enum: он остаётся в бандле

Чтобы понять, зачем вообще придумали const enum, вспомним важную деталь про обычный числовой enum. Он — это не только тип, но и настоящий объект, который живёт в рантайме. Компилятор превращает объявление enum в кусок реального JavaScript-кода, и этот код попадает в итоговую сборку (бандл) вашего приложения.

Обычно это удобно: благодаря такому объекту у числового enum работает, например, обратный маппинг (Direction[0] === 'Up'). Но за удобство надо платить: даже если во всём приложении вы используете лишь одно значение Direction.Up, в бандл всё равно уезжает весь объект-справочник целиком. Для одного enum это капля, но в большой кодовой базе такие капли складываются в лишние килобайты, которые пользователь честно скачивает.

Идея const enum: инлайнинг на этапе компиляции

Здесь на сцену выходит const enum. Пишется он почти как обычный enum — добавляется только слово const:

Ключевое слово const — это обещание компилятору: «значения членов не изменятся, они известны заранее». А раз значения известны на этапе сборки, компилятор может проделать фокус под названием инлайнинг (от английского inline — «встроить по месту»): вместо обращения Direction.Up он подставит в код само значение — число 0. Тогда объект-справочник становится не нужен, и его можно вообще не выпускать в рантайм.

Аналогия. Обычный enum — как ссылка «см. таблицу в приложении №3»: чтобы узнать значение, программа каждый раз лезет в справочник. const enum — как если бы редактор заранее подставил в текст нужное число прямо на место ссылки, а само приложение с таблицей из книги вырезал. Читателю больше некуда «лезть» — ответ уже перед глазами.

Плюс: нулевая рантайм-стоимость (в теории)

Если инлайнинг сработал, выгода очевидна. Объект в бандл не попадает — значит, финальный файл чуть меньше, а браузеру нечего исполнять при загрузке этого модуля. Для типов вроде «направление», «сторона света» или «единица измерения», где нужны только сами значения, а обратный маппинг и перебор ключей не важны, const enum выглядит как бесплатная оптимизация: пишете читаемое Direction.Up, а в рантайм уходит компактное 0.

Важная оговорка — «в теории». Всё описанное выше верно только тогда, когда компилятор действительно инлайнит значения. А инлайнинг зависит от того, как именно собирается проект. И вот здесь заканчивается реклама и начинаются ограничения, из-за которых в современных проектах const enum чаще всего только вредит.

Ограничения

У const enum есть несколько подводных камней. Первые два — принципиальные, а третий (про наш проект) полностью перечёркивает всю выгоду.

Нет обратного маппинга

Раз объекта в рантайме нет, то и искать в нём нечего. Обратный маппинг «число → имя», который есть у обычного числового enum, у const enum отсутствует. Более того, компилятор запрещает даже обращаться к члену по вычисляемому индексу:

Под isolatedModules инлайна НЕТ

Вот главное. Наш проект (Angular на esbuild) собирается в режиме isolatedModules. В этом режиме каждый файл компилируется независимо от остальных, и сборщик принципиально не заглядывает в определения из других файлов. А значит, он не может быть уверен, чему равно Direction.Up, и не рискует ничего инлайнить. Вместо подстановки числа он эмитит полный объект enum — ровно такой же, как у обычного enum.

Вывод суровый: в этом проекте const enum не даёт ровным счётом ничего. Вы получаете все ограничения (нет обратного маппинга, особые правила доступа), но не получаете единственный ради чего всё затевалось плюс — компактный вывод без объекта.

Когда использовать и когда избегать

Соберём всё в одну таблицу — от условий сборки зависит буквально всё:

Ситуация const enum инлайнится? Стоит использовать?
Проект на «чистом» tsc, без isolatedModules ✅ да, объекта в JS нет ✅ можно, если нужна только скорость
Проект с бандлером и isolatedModules (наш случай) ❌ нет, эмитится полный объект ❌ избегать — выгоды ноль
Библиотека с ambient .d.ts (declare const enum) ❌ вообще ошибка TS2748 ❌ избегать

Для нашего проекта рекомендация однозначна: const enum не использовать. Если нужен просто набор именованных констант с компактным выводом, возьмите обычный объект с as const — он предсказуем в любом сборщике, честно виден в рантайме и легко превращается в тип:

Коротко

  • Обычный enum оставляет в бандле объект-справочник; const enum задуман, чтобы этого объекта не было.
  • Идея: значения известны на этапе сборки, поэтому компилятор инлайнит их (Direction.Up → 0), а объект не выпускает.
  • В идеальном случае (обычный tsc) в JS остаются голые числа: const x = 0 /* Direction.Up */ — нулевая рантайм-стоимость.
  • У const enum нет обратного маппинга, а к членам нельзя обращаться по вычисляемому индексу (Level[0] — ошибка).
  • Под isolatedModules (наш проект) инлайна нет — эмитится полный объект, как у обычного enum. Выгода исчезает.
  • declare const enum под isolatedModules — ошибка TS2748; флаг preserveConstEnums и вовсе сохраняет объект, убивая смысл.
  • В этом проекте const enum стоит избегать — берите обычный объект с as const.
