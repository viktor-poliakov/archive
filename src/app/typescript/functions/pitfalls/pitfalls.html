Нюансы и подводные камни

Мы разобрали функции по частям: сигнатуры, параметры, типы возврата, rest, перегрузки и this. Осталось собрать в одном месте небольшие, но коварные тонкости — те самые, на которых спотыкаются даже опытные. Каждый пункт короткий: крошечный пример и вывод одной строкой.

1. Меньше параметров — это нормально

Первое, что удивляет новичка: почему arr.map(x => x * 2) работает, хотя map зовёт колбэк с тремя аргументами — элементом, индексом и самим массивом? Потому что в TypeScript функцию с меньшим числом параметров можно поставить туда, где ждут функцию с большим. Лишние аргументы вызывающий код всё равно передаст, а функция их просто не заметит.

Вывод. Функция может принимать меньше параметров, чем от неё ждут, — это безопасно, потому что лишние аргументы никак не мешают. Обратное запрещено: функция не вправе требовать больше аргументов, чем ей гарантированно дадут.

Возврат void разрешает вернуть что угодно

Родственная тонкость: если контекст ждёт функцию с типом возврата void, то фактически вернуть из неё можно значение любого типа — его всё равно никто не использует. Именно поэтому [1,2,3].forEach(n => arr.push(n)) не ошибка, хотя push возвращает число, а forEach ждёт void. Подробно этот механизм разобран на странице Типы возвращаемого значения.

Вывод. void в ожидаемой сигнатуре означает «результат игнорируется», а не «функция обязана ничего не возвращать».

2. Опциональный ? против union с undefined

Две записи выглядят почти одинаково, но ведут себя по-разному. Параметр name?: string можно вообще не передавать. А параметр name: string | undefined (без ?) передать обязательно — пусть даже со значением undefined. Разница — в том, обязателен ли сам аргумент в месте вызова.

Что можно в месте вызова name?: string name: string | undefined
Не передавать аргумент вообще ✅ да ❌ нет, аргумент обязателен
Передать undefined явно ✅ да ✅ да
Передать строку ✅ да ✅ да

Вывод. Нужно «поле можно опустить» — берите ?. Форму | undefined без ? используют редко: когда хотят заставить вызывающего осознанно передать «пусто», а не забыть аргумент по невнимательности. Больше про это — на странице Параметры функций.

3. strictFunctionTypes: функции и методы проверяются по-разному

Флаг strictFunctionTypes (входит в strict) делает проверку типов параметров строгой и безопасной — но только для функций, записанных как поле-функция (on: (e) => void). У параметров, записанных синтаксисом метода (on(e): void), проверка осталась мягкой. Это не баг, а намеренная «дырка», оставленная ради совместимости со множеством старых типов (например, DOM-обработчиков событий).

Форма записи Как проверяются параметры Небезопасная подстановка
Поле-функция: on: (e) => void строго (контравариантно) ✅ ловится ошибкой
Метод: on(e): void мягко (бивариантно) ❌ проходит молча

Вывод. Теорию про вариантность запоминать не обязательно — важно практическое: если хотите, чтобы TypeScript строго проверял параметры колбэка, объявляйте его полем-функцией, а не методом. И помните, что у методов эта проверка сознательно ослаблена.

4. Тип Function — избегайте

У TypeScript есть встроенный тип Function — казалось бы, «любая функция». Но по сути это any для функций: такое значение можно вызвать с любыми аргументами, а результат вызова имеет тип any. Никакой проверки ни аргументов, ни возврата — вся польза типизации пропадает.

Вывод. Никогда не пишите Function. Всегда указывайте точную сигнатуру: (x: number) => void. Если функция действительно может быть любой, честнее написать (...args: unknown[]) => unknown — это заставит вас аккуратно проверить аргументы и результат, в отличие от Function.

5. Перегрузки против объединений

Перегрузки кажутся мощным инструментом, но они многословны и легко расходятся с реализацией. В большинстве случаев то же самое выражается короче и безопаснее через объединение в одном параметре или через дженерик, когда тип результата зависит от типа аргумента.

Вывод. Сначала попробуйте объединение или дженерик — и только если форма вызова принципиально разная для разных аргументов, беритесь за перегрузки.

6. Неявный any в параметрах

Параметр без аннотации типа получает тип any — «неявный any». При включённом noImplicitAny (а он входит в strict) это ошибка компиляции. Функция с таким параметром теряет всю защиту типов: внутри с аргументом можно делать что угодно, и ни одна опечатка не будет поймана.

Вывод. Всегда аннотируйте параметры обычных функций. Исключение — колбэки, где тип параметра TypeScript выводит из контекста (как в arr.map(x => …)): там аннотация не нужна и даже избыточна.

7. Потеря this при передаче метода

Метод объекта «знает» свой this, только пока его вызывают через сам объект: counter.inc(). Если же передать counter.inc куда-то как колбэк (в setTimeout, обработчик события и т. п.), метод отрывается от объекта, и this теряется. Это чисто джаваскриптовое поведение, но TypeScript умеет предупредить о нём — если у метода объявлен параметр this.

Вывод. Передавая метод как колбэк, оборачивайте вызов в стрелку (() => obj.method()) или привязывайте контекст через bind. Подробно про природу this и способы его сохранить — на странице Типизация this.

Кратко

  • Меньше параметров — можно: функция с меньшим числом параметров подходит туда, где ждут больше (поэтому map(x => …) работает). Требовать больше, чем дадут, — нельзя.
  • Возврат void в ожидаемой сигнатуре разрешает вернуть значение любого типа — его игнорируют (подробнее).
  • x?: T — аргумент можно опустить; x: T | undefined — аргумент обязателен, но им может быть undefined.
  • strictFunctionTypes: параметры поля-функции проверяются строго, параметры метода — мягко (намеренная «дырка»).
  • Тип Function — это any для функций; вместо него всегда пишите точную сигнатуру вроде (x: number) => void.
  • Перегрузки берите в последнюю очередь — обычно хватает объединения или дженерика.
  • Неявный any в параметре — ошибка при noImplicitAny; аннотируйте параметры (в колбэках тип выводится из контекста).
  • Потеря this: передача obj.method как колбэка теряет контекст — спасают стрелка или bind.
