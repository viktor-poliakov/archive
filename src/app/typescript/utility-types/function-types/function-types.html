TypeScript/Утилитарные типы/ReturnType, Parameters

ReturnType, Parameters

ReturnType и Parameters — это рентген для функции. Представьте, что у вас уже есть готовая функция, и вам нужно узнать про неё две вещи: что она возвращает и какие аргументы принимает. Вместо того чтобы переписывать эти типы руками (и рисковать ошибиться), вы «просвечиваете» функцию насквозь и считываете типы прямо с неё. ReturnType читает тип результата, Parameters — типы аргументов. Как на медосмотре: не гадаем, что внутри, а смотрим на снимок.

Боль: типы, которые «разъезжаются»

Начнём с проблемы, которую эти утилитарные типы решают. Слово утилитарный тип (utility type) означает просто «готовый вспомогательный тип, встроенный в TypeScript»: вы даёте ему на вход другой тип, а он возвращает новый, как-то преобразованный. ReturnType и Parameters — два таких помощника, и оба работают с функциями.

Вообразим типичную ситуацию. У нас есть функция-фабрика (так называют функцию, чья задача — собрать и вернуть готовый объект). Она создаёт пользователя. А в другом месте программы нам понадобился тип этого пользователя. Первый порыв — описать его руками, заново:

На первый взгляд всё хорошо. Но приглядитесь: теперь у нас два источника правды об одном и том же объекте — тело функции makeUser и отдельный interface User. Стоит завтра добавить в фабрику поле email, а в интерфейсе про него забыть — и типы «разъедутся» (по-английски это называют drift, дрейф). Компилятор не подскажет, потому что для него это два независимых, ничем не связанных типа. Именно такие тихие рассинхроны и ловят наши «рентгены».

Главная идея страницы — DRY. DRY расшифровывается как Don't Repeat Yourself — «не повторяйся». Если один и тот же тип описан в двух местах, рано или поздно они разойдутся. ReturnType и Parameters позволяют держать один источник правды — саму функцию — и выводить все остальные типы из неё.

ReturnType<F>: считываем, что функция возвращает

Первый рентген — ReturnType. Вы передаёте ему тип функции, а он достаёт из него тип возвращаемого значения. Ничего переписывать не нужно: тип «считывается» с уже существующей функции.

Обратите внимание на разницу с предыдущим разделом. Там User был копией, которую мы поддерживали вручную. Здесь User — это производная от makeUser: они связаны навсегда. Добавите в фабрику новое поле — тип User подхватит его сам, без единой правки. Один источник правды, никакого дрейфа.

Ключевой шаг: маленькое слово typeof

В примере выше вы наверняка заметили странное слово typeof перед makeUser. Это самый важный и самый спотыкательный момент всей темы, поэтому разберём его медленно.

В TypeScript есть два разных мира: мир значений и мир типов. makeUser — это значение: конкретная функция, которую можно вызвать, передать в переменную, положить в массив. А ReturnType в угловых скобках ждёт не значение, а тип. Просто написать ReturnType<makeUser> нельзя — это всё равно что передать саму коробку туда, где просят прочитать этикетку с неё.

Мостик между двумя мирами и есть оператор typeof. Он берёт значение и отвечает на вопрос «какого ты типа?» — то есть возвращает тип этого значения. Для функции это будет её сигнатура: какие аргументы, что возвращает.

Типичная ошибка: забыли typeof

Раз уж typeof так легко упустить, посмотрим на ошибку в лицо — чтобы потом сразу её узнавать. Если написать имя функции без typeof, компилятор споткнётся: он ждал тип, а получил значение.

Сообщение «'makeUser' refers to a value, but is being used as a type here» («'makeUser' — это значение, но используется как тип») — прямой намёк, что вы забыли typeof. TypeScript даже подсказывает готовое исправление: «Did you mean 'typeof makeUser'?». Запомните простое правило-мнемонику: функция — это значение; чтобы получить её тип, ставим перед ней typeof.

Когда typeof НЕ нужен. Если у вас уже есть именно тип функции (например, type Fn = (x: number) => string), то писать typeof не надо — он нужен только чтобы превратить значение (реальную функцию) в тип. Пишете ReturnType<Fn> напрямую. А вот из живой функции makeUser тип добывается только через typeof makeUser.

Parameters<F>: считываем типы аргументов

Второй рентген — Parameters. Он смотрит на функцию и возвращает типы её аргументов, собранные в кортеж. Кортеж (tuple) — это массив фиксированной длины, где у каждой позиции свой тип: первый элемент одного типа, второй — другого. Как раз то, что нужно, чтобы описать список аргументов «по порядку».

Достаём один аргумент: индексация кортежа

Раз Parameters возвращает кортеж, из него можно взять тип отдельного аргумента — по его номеру (индексу). Индексы начинаются с нуля: [0] — первый аргумент, [1] — второй, и так далее. Синтаксис такой же, как при обращении к элементу массива, только применяется он к типу.

Это очень удобно на практике. Допустим, у вас есть отдельная функция, которая проверяет только имя пользователя. Вместо того чтобы гадать «а какого типа должно быть имя?», вы берёте этот тип прямо у источника — Parameters<typeof createUser>[0]. Если сигнатуру createUser когда-нибудь изменят, ваша проверка обновится автоматически.

Практика: один источник правды для формы

Сложим оба рентгена вместе на реалистичном примере — форме профиля. Одна фабрика buildProfile описывает, из чего состоит профиль. А все производные типы — и тип готового объекта, и тип набора полей — мы выводим из неё, не дублируя ничего руками.

Заметьте, как красиво всё сходится: saveProfile принимает Profile, а buildProfile возвращает ровно такой же тип — потому что Profile и есть его ReturnType. Они физически не могут разойтись. Это и есть сила подхода: меняете фабрику в одном месте — вся цепочка типов подстраивается сама.

Практика: тип действия из его создателя

Ещё один очень частый приём — вывести тип «действия» (action) из функции, которая его создаёт. Это классика стейт-менеджеров вроде Redux, но идея универсальна: есть функция-создатель, и мы хотим тип того, что она производит, — не описывая его отдельно.

Здесь cartReducer всегда работает с типом, синхронным с addToCart. Добавите в создатель новое поле — тип действия обновится, и редьюсер сразу увидит новое поле. Никакого ручного дублирования структуры действия.

Подводный камень: асинхронные функции

Последнее, о чём важно предупредить заранее. Если функция асинхронная (объявлена через async), она всегда возвращает Promise — «обещание» будущего значения. Поэтому ReturnType честно достанет именно Promise, а не тот объект, что лежит внутри него.

Чтобы «развернуть» Promise и добраться до типа внутри него, есть отдельный утилитарный тип Awaited. Его удобно надеть поверх ReturnType: сначала ReturnType достаёт Promise<...>, а Awaited снимает обёртку. Подробнее — на странице про Awaited.

Как это устроено внутри. И ReturnType, и Parameters — не магия компилятора, а обычные типы, написанные через условные типы и ключевое слово infer («вывести» тип из шаблона). Знать это для использования не обязательно, но если захочется заглянуть «под капот» — загляните туда (по желанию).

Коротко

  • ReturnType<F> — «рентген результата»: достаёт тип того, что функция возвращает. type User = ReturnType<typeof makeUser>.
  • Parameters<F> — «рентген аргументов»: возвращает кортеж типов аргументов. Отдельный аргумент берут по индексу: Parameters<typeof fn>[0].
  • Всегда через typeof. Функция — это значение; чтобы отдать её тип в угловые скобки, пишем typeof fn. Забыли typeof — получите ошибку «refers to a value, but is being used as a type».
  • Смысл — DRY. Оба типа выводятся из самой функции, поэтому производные типы не могут разойтись с ней. Один источник правды вместо ручных копий.
  • Асинхронность. У async-функции ReturnType вернёт Promise<...>; чтобы снять обёртку, оберните результат в Awaited.

Оба типа стоят на фундаменте дженериков — если <F> в угловых скобках выглядит незнакомо, начните оттуда. Внутри они устроены через условные типы с infer. А для асинхронных функций дальше по программе — Awaited, который снимает с результата обёртку Promise.
