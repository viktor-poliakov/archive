Реализация интерфейсов

Представьте техническое задание (ТЗ): заказчик выписал список требований — что должно уметь готовое изделие. Интерфейс в TypeScript — это и есть такое ТЗ, контракт формы. А запись class ... implements ... — это исполнитель, который берётся выполнить ТЗ. Компилятор при этом играет роль приёмки: он проверяет, что все пункты ТЗ закрыты, и не пропускает работу, если чего-то не хватает. Один важный нюанс сразу: implements не выдаёт готовый код — он только сверяет форму. Весь код исполнитель пишет сам.

Зачем это нужно: гарантия формы

Интерфейс сам по себе — просто описание. Он говорит «объект такой формы обязан иметь метод log», но никого не заставляет этой формы придерживаться. Пока мы пишем класс «на глазок», легко случайно отклониться от ТЗ — опечататься в имени метода, забыть параметр, вернуть не тот тип. Компилятор такую ошибку, конечно, поймает, но не там, где удобно:

Аналогия. Интерфейс — это чек-лист приёмки, вывешенный на стене цеха. Он ничего не производит сам. Но как только исполнитель говорит «беру этот заказ» (implements), приёмщик (компилятор) идёт по чек-листу пункт за пунктом и не подписывает акт, пока хоть один пункт не закрыт. Если базовые классы JS ещё в новинку — загляните в JS: классы, основы.

class X implements I — проверка формы

Синтаксис простой: после имени класса пишем ключевое слово implements и имя интерфейса. Это обещание: «класс имеет форму, которую требует I». Компилятор тут же проверяет обещание.

implements не наследует реализацию

Это главное, что путают новички. Слово implements похоже на extends, но делает совсем другое. implements ничего не приносит внутрь класса — интерфейс не содержит кода, только описание формы (сигнатуры методов без тел). Значит, весь код класс обязан написать сам:

Несколько интерфейсов: implements A, B

Исполнитель может взяться сразу за несколько ТЗ. Интерфейсы после implements перечисляются через запятую, и класс обязан закрыть требования каждого из них. Это удобно, когда объект играет несколько ролей одновременно: он и логирует, и умеет сериализоваться.

Компилятор проверит форму по обоим контрактам: пропусти класс метод toJSON — и загорится incorrectly implements interface 'Serializable', ровно как раньше с Logger. Количество интерфейсов при этом не ограничено — можно писать implements A, B, C и дальше.

extends и implements: в чём разница

Оба слова связывают класс с чем-то «сверху», но роли у них разные. Сведём различия в таблицу — держите её в голове, и путаницы больше не будет.

Критерий extends (наследование) implements (реализация)
С чем связывает с классом (базой) с интерфейсом (контрактом)
Приносит готовый код? ✅ да, тело методов наследуется ❌ нет, только форма
Что делает компилятор переносит члены базы вниз проверяет, что форма совпала
Сколько сущностей сразу ❌ один класс (одна база) ✅ много интерфейсов через запятую
Порядок в объявлении идёт первым идёт после extends

implements вместе с extends

Раз это разные механизмы, их можно применять одновременно. Класс берёт готовый код у базы через extends и заодно обещает выполнить контракт через implements. Порядок в объявлении строгий: сначала extends, потом implements.

Обратите внимание, как делятся обязанности. Поле name и метод describe() пришли готовыми от базы Device (это работа extends). А метод log из контракта Logger пришлось написать самому — интерфейс его не дал, лишь потребовал (это работа implements). Если бы Printer переопределял метод базы Device, к нему нужно было бы добавить ключевое слово override — в этом проекте оно обязательно; но log базой не объявлен, поэтому здесь override не нужен.

Практика: один контракт — много реализаций

Коротко

  • Интерфейс — это ТЗ (контракт формы), а class X implements I — исполнитель, который берётся его выполнить. Компилятор играет роль приёмки.
  • implements только проверяет форму. Недостающий член → ошибка Class 'X' incorrectly implements interface 'I'. Property '...' is missing, причём прямо на классе.
  • Кода implements не приносит. Интерфейс не содержит реализации — все тела методов класс пишет сам. Этим он отличается от extends, который наследует готовый код.
  • Интерфейсов может быть много: implements A, B, C — класс обязан закрыть требования каждого.
  • extends и implements совместимы: сначала extends (берём код базы), затем implements (сверяем форму с контрактом).
  • Зачем всё это — взаимозаменяемость: код зависит от контракта, а не от класса, поэтому реализации (ConsoleLogger, ArrayLogger, …) можно свободно подменять.

Дальше стоит освежить сами Интерфейсы — что вообще можно в них описывать. Дженерик-контракты живут на странице Дженерики в классах (ArrayStack<T> implements Stack<T>). А если контракту нужна ещё и общая реализация «по умолчанию» — сравните implements с абстрактными классами: интерфейс задаёт только форму, абстрактный класс может дать и часть готового кода.
