Абстрактные классы

Абстрактный класс — это недостроенный чертёж, или бланк с обязательными пропусками. Сам по себе он неполный: по нему нельзя изготовить готовое изделие (создать объект через new запрещено). Но он задаёт скелет — общие детали и список «пустых граф», которые наследник обязан заполнить. Такой родитель не просто описывает форму, как интерфейс, — он ещё и приносит готовый общий код. Если классы в целом пока в новинку, начните с основ классов в JS и основ классов в TS.

Зачем нужны абстрактные классы

Представьте, что вы пишете калькулятор площадей для разных фигур: круга, прямоугольника, треугольника. У каждой фигуры своя формула площади, но есть и общее поведение — например, метод describe(), который печатает «Площадь ≈ …». Общий код хочется написать один раз в классе-родителе, а формулу площади оставить каждому наследнику своей.

Нам нужен способ честно сказать компилятору: «этот класс — только каркас, создавать его напрямую нельзя, а метод area() — обязательная пустая графа, которую заполнит наследник». Ровно это и делает ключевое слово abstract.

abstract class: экземпляр создать нельзя

Ставим перед словом class модификатор abstract — и класс превращается в «недостроенный чертёж». Внутри него метод area() тоже помечаем abstract и пишем без тела — только сигнатуру (имя, параметры, тип результата). Это и есть «обязательная пустая графа». А describe() оставляем обычным методом с телом — это общий код.

Обратите внимание: describe() спокойно вызывает this.area(), хотя тела у area() здесь ещё нет. Это не ошибка — компилятор гарантирует, что к моменту реального вызова наследник обязательно даст area() настоящее тело. Пока же попытка сделать объект прямо из Shape обрывается сразу:

Почему new запрещён. Абстрактный класс неполон по определению: часть его методов — пустые графы. Если бы TypeScript позволил создать такой объект, вызов area() у него привёл бы в никуда (тела-то нет). Поэтому new разрешён только для конкретных (не-абстрактных) наследников, где все графы заполнены.

abstract-метод: наследник обязан его реализовать

Теперь «достроим чертёж». Создаём конкретный класс Circle, наследуем Shape через extends — и обязаны дать area() настоящее тело со своей формулой. Общий код в базе: паттерн «шаблонный метод»

Ключевое отличие абстрактного класса от интерфейса в том, что он умеет нести готовый, уже написанный код. Метод describe() мы написали в базе один раз — и все наследники получают его бесплатно, ничего не дублируя. При этом внутри describe() зовёт абстрактный area(), у которого у каждого наследника своя реализация. Получается элегантный приём: неизменный каркас живёт в базе, а переменная часть подставляется наследником.

Такой приём называют шаблонным методом (template method): базовый метод задаёт общий «шаблон» действий, а «дырки» в нём заполняют абстрактные методы наследников. Отдельно отметим строку const shapes: Shape[]: создавать сам Shape нельзя, но использовать его как тип — можно и нужно. Массив «фигур вообще» прекрасно хранит и круги, и прямоугольники — ведь оба они являются Shape.

Реализация abstract-метода не требует override

Здесь новичка подстерегает тонкость. В проекте включена строгая опция noImplicitOverride: она требует писать ключевое слово override, когда наследник переопределяет метод базы. Но реализация abstract-метода — это не переопределение! В базе у area() не было тела — был лишь контракт, обещание. Мы даём этот метод впервые, а не заменяем существующую реализацию. Поэтому override на area() ставить не обязательно — обычно его и не пишут. Написать всё же можно (ошибки не будет, ведь area() в базе объявлен), но это лишнее:

Правило на пальцах. Спросите себя: «в базе у этого метода было тело?» Если было и вы его меняете — это переопределение, нужен override. Если тела не было (метод abstract) — вы реализуете контракт впервые, и override не обязателен (написать его можно, но обычно не пишут). Это ровно та же логика, что и с реализацией интерфейса: там тоже override не ставят.

Абстрактный класс и интерфейс: в чём разница

Начинающие часто путают абстрактный класс с интерфейсом — оба ведь описывают «что класс должен уметь». Разница фундаментальная. Интерфейс — это только форма: список сигнатур без единой строчки кода, он полностью исчезает при компиляции и ничего не хранит. Абстрактный класс — это настоящий класс: он несёт готовые (реализованные) методы, может хранить поля-состояние и существует в рантайме.

Отсюда и практический выбор: implements лишь проверяет форму — реализацию каждого метода придётся написать вручную в каждом классе; extends абстрактного класса наследует готовый код — общий describe() достаётся наследнику бесплатно. Мостик к деталям — на странице Реализация интерфейсов.

Критерий Абстрактный класс Интерфейс
Готовый код (тела методов) ✅ да, общий код в базе ❌ нет, только сигнатуры
Хранит состояние (поля со значением) ✅ да ❌ нет
Существует в рантайме ✅ да, это класс ❌ нет, стирается при компиляции
Сколько можно «взять» одному классу ❌ только один (extends) ✅ сколько угодно (implements A, B)
Свой объект через new ❌ нельзя (только у наследника) ❌ нельзя (это не значение)

Коротко

  • Абстрактный класс (abstract class) — «недостроенный чертёж»: задаёт скелет, но сам неполон. Создать его объект нельзя — new Shape() даёт ошибку «Cannot create an instance of an abstract class».
  • abstract-метод объявляется без тела — только сигнатура. Это обязательная «дыра»: наследник обязан её реализовать, иначе ошибка «does not implement inherited abstract member».
  • Абстрактный класс может иметь и обычные методы с телом — общий код для всех наследников. Приём, когда общий метод (describe()) вызывает абстрактный (area()), называют шаблонным методом.
  • Реализация abstract-метода — это не переопределение, поэтому override на неё ставить не обязательно (но и не запрещено — можно как угодно). А вот переопределение обычного метода базы override требует (в проекте включён noImplicitOverride).
  • Конструктор наследника обязан вызвать super(); сам abstract-класс можно свободно использовать как тип (например, Shape[]), просто не создавать через new.
  • Отличие от интерфейса: интерфейс — только форма (без кода и состояния, стирается при компиляции); абстрактный класс несёт готовый код и поля-состояние. Отсюда: implements лишь проверяет форму, extends наследует реализацию.
